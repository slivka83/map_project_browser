## §1. Критическая ошибка: двойной переворот знака для конических проекций южного полушария

**Файл:** `src/utils/projectionMapper.ts:243`  
**Функция:** `getD3Projection` — ветка `conic`

### Проблема

Для конической проекции с южным полушарием (`coneHemisphere === 'south'`, `phiOrigin = -30`) D3-проекция получает стандартные параллели с **северным** знаком (30°, 45°) вместо южного (-30°, -45°). Причина — двойное умножение на знак:

```typescript
// Текущий код (projectionMapper.ts, строки 242–244):
const sign = state.coneHemisphere === 'south' ? -1 : 1;              // знак = -1 (юг)
const phi1Raw = signedStandardParallelDeg(phiOrigin) * sign;         // -30 * (-1) = +30  ← ДВОЙНОЙ ПЕРЕВОРОТ
const phi1 = Math.abs(phiOrigin) < 10 ? (30 * sign) : phi1Raw;      // → +30 в D3
```

Функция `signedStandardParallelDeg(-30)` **уже возвращает -30** (она сохраняет знак phiOrigin). Повторное умножение на `sign = -1` даёт `+30` — северное значение.

### Физическое последствие

- **3D-конус** (через `computeCone` в `auxSurfaceGeometry.ts:370`) правильно строится в южном полушарии: `flip = -1`, `sign = -1`, пересечения с глобусом на широтах -30° и -45°.
- **2D-карта** (через D3 `geoConicEquidistant().parallels([30, 45])`) строится с **северным** конусом — стандартные параллели на +30° и +45°.
- Проекция, отрисовываемая на 2D-карте, НЕ СОВПАДАЕТ с тем, что показывает 3D-сцена. Пользователь видит разные геометрии.
- Визуальное следствие: линии пересечения и искажения на 2D-карте расходятся с 3D-конусом.

### Как исправить

Убрать двойное умножение на `sign`. Достаточно либо `signedStandardParallelDeg(phiOrigin)` (она уже знаковая), либо `standardParallelDeg(phiOrigin) * sign` (модуль × знак полушария):

```typescript
// Исправление (вариант 1):
const phi1 = signedStandardParallelDeg(phiOrigin);
// Исправление (вариант 2):
const phi1 = standardParallelDeg(phiOrigin) * sign;
```

Аналогично исправить `phi2`:
```typescript
// Текущий код (проекция):
const phi2 = state.stdParallel2 != null ? state.stdParallel2 * sign : phi1;
// Исправление:
const phi2 = state.stdParallel2 != null ? state.stdParallel2 : phi1;
```

**Также требуется синхронное исправление** в `projectionMapper.ts` для функции `computeAreaDistortion` (строка 367) и `referenceAreaScale` (строка 428), где используется та же самая логика:

```typescript
// В computeAreaDistortion (строка 367):
const phi1 = Math.abs(params.phiOrigin) < 10 ? 30 : Math.abs(params.phiOrigin);
```

Здесь тоже `phi1` вычисляется как модуль, а ниже умножается на `sign`. Проверить, что `localAreaScale` вызывается с правильным знаком широты для южного полушария.

### Почему тесты не нашли

В `physics.test.ts` нет теста конических проекций с южным полушарием. Тест `'conic secant surface passes through both standard parallels'` использует положительные значения (30, 50). Нужно добавить тест с `phiOrigin = -30`, `stdParallel2 = -45`, `coneHemisphere = 'south'`, проверяющий что D3-проекция отображает широту -30° в центр карты, и что пересечения конуса в 3D и 2D совпадают по широте.

## §2. Ошибка в визуализации лучей для ортографической проекции

**Файл:** `src/utils/auxSurfaceGeometry.ts:937–938` и `:1055–1056`  
**Функции:** `computeCentralMeridianRays` и `projectToAuxWorld`

### Проблема

Для ортографической проекции (`azLight === 'infinity'`) начальная точка луча (`start`) ставится на **неправильной** стороне сцены:

```typescript
// Текущий код:
start = [end[0] + normal[0] * PARALLEL_LEN, end[1] + normal[1] * PARALLEL_LEN, end[2] + normal[2] * PARALLEL_LEN];
```

`normal` — это внешняя нормаль сферы в точке касания (направлена ОТ центра глобуса). `end` — точка на проекционной плоскости (касательной к глобусу с внешней стороны). Значит `end + normal * LEN` — точка ЕЩЁ ДАЛЬШЕ от глобуса, за плоскостью.

### Физически неправильная картина

Луч рисуется как `start → globe → end`. При текущем коде:
- `start` — далеко за плоскостью (в направлении normal)
- `globe` — на сфере (на расстоянии R от центра)
- `end` — на плоскости (расстояние ≥ R от центра)

Это означает, что луч движется **от плоскости назад** к сфере, а затем **снова к плоскости**. Такой зигзаг физически бессмыслен: свет при ортографической проекции идёт параллельными лучами из бесконечности **по направлению к плоскости**, проходя сквозь сферу и падая на плоскость за ней. Направление света: `-normal` → глобус → плоскость.

### Физически правильная картина

Луч должен идти:
- `start` — далеко **перед** глобусом в направлении `-normal` (там, где «зритель в бесконечности»)
- `globe` — точка на сфере
- `end` — точка на плоскости (за сферой, в направлении normal)

### Как исправить

```typescript
// В computeCentralMeridianRays (строка 937–939):
if ((family === 'azimuthalPerspective') && azLight === 'infinity') {
    start = [globe[0] - normal[0] * PARALLEL_LEN, globe[1] - normal[1] * PARALLEL_LEN, globe[2] - normal[2] * PARALLEL_LEN];
}

// Аналогично в projectToAuxWorld (строка 1055–1057):
if ((family === 'azimuthalPerspective') && azLight === 'infinity') {
    start = [globe[0] - normal[0] * PARALLEL_LEN, globe[1] - normal[1] * PARALLEL_LEN, globe[2] - normal[2] * PARALLEL_LEN];
}
```

Либо, как вариант, оставить `end + normal*LEN` если визуально сейчас это смотрится нормально, но тогда назвать это «light comes from the plane side» и признать, что модель не соответствует физике света. Сейчас это именно ошибка направления: лучи идут не от источника к цели, а зигзагом.

### Почему тесты не нашли

Тест `'every central-meridian ray's globe endpoint is the true 3D point'` проверяет только координаты `globe`, но не направление луча (start → globe → end). Нужно добавить проверку: для ортографической проекции вектор `end - globe` должен быть параллелен `normal`, а вектор `globe - start` должен быть сонаправлен с `normal` (а не противоположен).

## §3. Ложная метка «Сохраняет углы» для гномонической проекции

**Файл:** `src/utils/projectionVariants.ts:345, 359`

### Проблема

```typescript
// gnomonic:
distortion: 'conformal',   // ← используется ТОЛЬКО для маршрутизации azLight → D3, не для математики
propertyLabel: 'Сохраняет углы',  // ← физически ложно!
```

Гномоническая проекция **НЕ конформна**. Её уникальное свойство: все большие круги (ортодромии) отображаются прямыми линиями. Углы НЕ сохраняются.

Комментарий в коде (строка 336–343) это признаёт:
> The gnomonic projection is NOT conformal — it is the unique projection where every great circle is a straight line; the 'conformal' value here is a placeholder and is ignored in the math.

Но пользователь в интерфейсе видит «Сохраняет углы» — прямая дезинформация.

### Как исправить

В `projectionVariants.ts` для варианта `gnomonic`:
```typescript
propertyLabel: 'Ортодромии = прямые линии (не конформна)',
```

Аналогично, для ортографической (`orthographic`):
```typescript
propertyLabel: 'Вид сферы из бесконечности (не конформна)',
```

(Там уже стоит адекватный label, но поле `distortion: 'conformal'` всё равно сбивает с толку. Лучше поменять `distortion` на `'equidistant'` как placeholder — никакая из трёх стандартных категорий не подходит для ортографической и гномонической, но хотя бы `equidistant` не врёт про сохранение углов.)

## §4. Неверная модель освещения для равнопромежуточной цилиндрической (equirectangular)

**Файл:** `src/utils/projectionVariants.ts:118–139`

### Проблема

```typescript
equirectangular: {
    azLight: 'infinity',
    lightIsParallel: true,
    ...
}
```

Равнопромежуточная цилиндрическая проекция (x = λ·cos φₛ, y = φ) — это аналитическая формула, а не физическая проекция. Она НЕ соответствует ортографическому проецированию на цилиндр (с параллельными лучами из бесконечности). Центральная проекция из центра глобуса (`azLight: 'center'`) была бы хоть сколько-то ближе к физической модели «цилиндр касается глобуса, разворачиваем его». Параллельные лучи создают неверную визуализацию.

### Как исправить

Для `equirectangular` и любых других цилиндрических проекций без физической оптической модели свет должен быть из центра глобуса:

```typescript
azLight: 'center',
lightIsParallel: false,
```

Либо альтернатива: оставить `lightIsParallel: false`, `azLight: 'center'` (лучи из центра). Разница между `lightIsParallel` и `azLight: 'infinity'` тонкая: `lightIsParallel` управляет только положением `start` для лучей центрального меридиана, а `azLight` управляет выбором D3-проекции для азимутальных. Для цилиндрических D3-проекция не зависит от `azLight`, поэтому менять надо только `lightIsParallel`.

## §5. `scaleFactor` не заблокирован для вертикальной/наклонной перспективы

**Файл:** `src/utils/projectionVariants.ts:472–555`

### Проблема

```typescript
verticalPerspective: {
    lockedScaleFactor: null,    // ← ползунок масштаба активен
    ...
}
tiltedPerspective: {
    lockedScaleFactor: null,    // ← ползунок масштаба активен
    ...
}
```

Для вертикальной и наклонной перспективы масштаб картинки полностью определяется высотой спутника (`azHeight`) и наклоном (`azTiltDeg`). Ползунок `scaleFactor` дублирует эту функцию, но:
- Меняет размер проекции и вспомогательной плоскости
- НЕ меняет положение спутника
- Создаёт рассогласование: спутник неподвижен, а плоскость проекции сжимается/расширяется

### Как исправить

```typescript
verticalPerspective: {
    lockedScaleFactor: 1,       // заблокировать
    ...
}
tiltedPerspective: {
    lockedScaleFactor: 1,       // заблокировать
    ...
}
```

## §6. Параметр `circleRadiusKm` не влияет на 2D-карту

**Файлы:** `src/utils/projectionMapper.ts:273–279` и `Map2D.tsx`

### Проблема

Для азимутальных математических проекций (`azimuthalMath`) параметр `circleRadiusKm` масштабирует D3-проекцию:

```typescript
const mathScale = circleRadiusToScale(circleRadiusKm) * MAP_SCALE * scaleFactor;
proj.scale(mathScale);
```

Но затем `fitProjectionToView` в `Map2D.tsx` **перезаписывает** этот масштаб, подгоняя проекцию под размеры контейнера. В результате:
- 2D-карта **не меняется** при изменении `circleRadiusKm` (она всегда показывает одну и ту же область ±85°)
- 3D вспомогательная плоскость **меняется** (она зависит от `circleRadiusKm` через `computeAuxSurfaceParams`)
- 2D и 3D расходятся: на 2D видно больше, чем «вмещает» 3D-плоскость, или наоборот

### Как исправить

**Вариант А (проще):** Сделать, чтобы `fitProjectionToView` использовал не фиксированный `FIT_SPHERE` (±85°), а область, зависящую от `circleRadiusKm`. Например, ограничить подгонку широтным поясом, соответствующим радиусу круга:

```typescript
// В Map2D.tsx: вместо FIT_SPHERE создать custom fit-объект
// на основе текущего circleRadiusKm
```

**Вариант Б:** Перестать перезаписывать масштаб для `azimuthalMath`, разрешив проекции иметь «родной» масштаб. Тогда `circleRadiusKm` будет напрямую влиять на видимый размер карты.

## §8. (Низкий приоритет) Твёрдый клип широт в цилиндрических проекциях

**Файл:** `src/utils/projectionMapper.ts:46`

### Проблема

```typescript
const clampPhi = (φ: number): number => Math.max(-clipRad, Math.min(clipRad, φ));
```

Для равнопромежуточной цилиндрической проекции широты > 85° «схлопываются» в одну линию (все они дают y = 85°). Для равноугольной и равновеликой такого схлопывания нет — функция остаётся гладкой вплоть до 85° и только потом обрезается.

Хотя это и не ошибка физики (конечный цилиндр действительно не может вместить полюса), с точки зрения восприятия пользователем карта должна вести себя одинаково для всех трёх типов искажения.

### Как исправить

Для равнопромежуточной проекции логарифмически «сжимать» широты выше 85°, чтобы полюсная область плавно переходила в край цилиндра:

```typescript
// Вместо твёрдого clampPhi для equidistant:
if (distortion === 'equidistant') {
    const logisticClamp = (φ: number) => {
        const k = 0.15; // крутизна сжатия
        return clipRad * Math.tanh(φ / (clipRad * k));
    };
}
```

Либо оставить как есть, но добавить комментарий в UI, что цилиндр имеет конечную высоту и точки выше 85° не проецируются.
