## 1. Критические баги

### 1.1 Сломанный конечный автомат линейки (Ruler)

**Файл:** `src/store/useAppStore.ts:337` → `src/components/Map2D.tsx:183-211`

При включении линейки (`setRulerActive(true)`) store выставляет `rulerMode = 'first'`. Однако обработчик клика в `Map2D.tsx` проверяет:

```ts
if (mode === 'off' || mode === 'done' || mode === 'second') {
    // записать точку 1
} else {
    // записать точку 2  ← попадаем сюда при mode='first'
}
```

При `mode='first'` клик уходит в ветку `else` и записывает **вторую** точку без первой. В результате:
- Первый клик после включения линейки ставит только красную точку (без линии и расстояния).
- Второй клик сбрасывает на `first`, ставит точку 1.
- Третий клик ставит точку 2 — только теперь появляется линия.

**Как исправить:** заменить `setRulerActive(true)` чтобы он устанавливал `rulerMode = 'off'`, или добавить обработку `mode === 'first'` в условие клика.

### 1.2 Спутник в 3D сцене на порядки дальше, чем нужно

**Файл:** `src/components/LightSource.tsx:42`

```ts
computeSatellitePosition(phiOrigin, lambda0, azHeight, RADIUS, RADIUS)
//                                            ^^^^^^  ^^^^^^
//                                         earthRadiusKm, modelRadius
```

Сигнатура: `computeSatellitePosition(phi0, lambda0, heightKm, earthRadiusKm=6371, modelRadius=RADIUS)`.
Параметр `earthRadiusKm` используется для перевода `heightKm` из км в модельные единицы через `scale = modelRadius / earthRadiusKm`.

Передача `RADIUS=10` в качестве `earthRadiusKm` даёт `scale = 10/10 = 1`, поэтому высота спутника = `azHeight` (например 400) в модельных единицах — при радиусе глобуса 10. Спутник оказывается в 40 раз дальше от глобуса, чем должен.

Сравните с правильным вызовом в `computeCentralMeridianRays` (строка 920):
```ts
computeSatellitePosition(phiOrigin, lambda0, azHeight ?? 400)
// earthRadiusKm = 6371 (default), scale = 10/6371 ≈ 0.00157
// h = 400 * 0.00157 ≈ 0.628 модельных единиц
```

**Как исправить:** заменить `RADIUS, RADIUS` на просто вызов без лишних аргументов или `6371, RADIUS`.

### 1.3 Наклон (gamma) цилиндрических проекций не влияет на 2D карту

**Файлы:** `src/utils/projectionMapper.ts:226-230`, `src/utils/auxSurfaceGeometry.ts:443-453`

В `getD3Projection` для семейства `cylindrical`:
```ts
const rotZ = 0;
proj.rotate([-(effLambda0), -phiOrigin, rotZ])
```
Gamma **нигде не участвует** в D3-вращении. Это означает, что:
- Для `obliqueMercator` (единственный цилиндрический вариант с unlocked gamma) слайдер наклона меняет только 3D цилиндр.
- 2D карта **не меняется** при изменении gamma.
- 3D и 2D виды рассинхронизированы.

Комментарий в `auxSurfaceGeometry.ts:443-453` подтверждает, что так задумано («карта инвариантна к повороту трубы»), но для **наклонного Меркатора** это физически неверно: в реальной картографии наклон цилиндра меняет вид проекции (сравните прямой, поперечный и косой Меркатор — это разные карты).

AGENTS.md утверждает: «gamma is folded into phiOrigin (rotate([-(lambda0), -(phiOrigin + gamma), 0]))» — но в коде этого нет.

**Как исправить:** либо встроить gamma в `phiOrigin` для цилиндрического семейства: `rotate([-(effLambda0), -(phiOrigin + gamma), 0])`, либо (более правильно) использовать `rotZ = -gamma` как для других семейств. Второй вариант потребует тестирования, не сломает ли он геометрию `makeCylindricalProjection`.

### 1.4 2D кольца пересечения неподвижны при наклоне цилиндра

**Файл:** `src/components/Map2D.tsx:167`

```ts
family === 'cylindrical' ? 0 : params.gamma
```

Для цилиндрического семейства gamma жёстко зануляется при вычислении 2D колец пересечения. При этом:
- 3D кольца (`IntersectionDisks.tsx`) **двигаются** с наклоном (gamma передаётся через `surface` из `GlobeScene`).
- 2D кольца остаются на месте (как для прямого цилиндра).

AGENTS.md утверждает обратное: «a tilted cylinder's ring MOVES with the tilt, exactly like the 3D ring».

**Как исправить:** передавать реальный gamma и для цилиндрического семейства. Для правильного отображения на 2D карте потребуется также исправить п. 1.3 (gamma в D3-проекции).

## 2. Серьёзные логические ошибки

### 2.1 EPSG:9841 (Ортографическая): неверный тип искажения

**Файл:** `src/constants/epsgPresets.ts:47`

```ts
{ code: 'EPSG:9841', name: 'Ортографическая', ...,
  params: { variant: 'orthographic', ..., distortion: 'equidistant', ... } }
```

Но определение варианта (`projectionVariants.ts:420-461`) задаёт `distortion: 'conformal'`. При применении пресета `distortion` становится `'equidistant'`, что противоречит `variantDef('orthographic').distortion`. Хотя `getD3Projection` для азимутальных перспективных не использует `distortion` напрямую, `ProjectionSummary` и любой код, читающий `distortion`, будут показывать неверное значение.

**Как исправить:** `distortion: 'conformal'`.

### 2.2 Период орбиты (SOM) не используется

**Файл:** `src/utils/auxSurfaceGeometry.ts:801-820`

```ts
export function computeOrbitalPath(
  t: number, inclination: number,
  _period: number,  // ← не используется
  nodeLongitude: number, ...
)
```

Параметр `_period` объявлен, но нигде не задействован. Функция возвращает позицию на круговой орбите независимо от периода. Слайдер «Период (мин)» в UI не имеет эффекта.

**Как исправить:** использовать period для масштабирования скорости (`ang = t * (2π / periodMinutes)`), либо убрать параметр из интерфейса.

### 2.3 Дубликат функции нормализации вектора

**Файл:** `src/utils/auxSurfaceGeometry.ts:81-89`

```ts
export function vec3Normalize(v: Vec3): Vec3 { ... }  // export
function normalize(v: Vec3): Vec3 { ... }              // не export, идентичное тело
```

Две функции делают одно и то же. `normalize` используется только в `computeTangentBasis` и `basisFromNormal` — можно заменить на `vec3Normalize` и удалить дубликат.

### 2.4 `computePerpendicularNormals` игнорирует поверхность

**Файл:** `src/utils/auxSurfaceGeometry.ts:657-676`

Параметр `_surface` (с префиксом `_`) не используется. Функция создаёт нормали фиксированной длины 0.4 от точек глобуса ВСЕГДА радиально наружу, без учёта реальной формы вспомогательной поверхности. Для цилиндра нормали должны упираться в цилиндр, для конуса — в конус, для плоскости — в плоскость.

Сейчас метод визуализации «Перпендикулярные нормали» выглядит одинаково для всех семейств и неиллюстративен.

**Как исправить:** вычислять точку пересечения луча из точки глобуса по нормали с реальной поверхностью (цилиндр/конус/плоскость).

---

### 2.5 Визуализация «Капли и частицы» не связана с реальной проекцией

**Файл:** `src/utils/auxSurfaceGeometry.ts:680-703`

`computeParticleTrajectories` размещает частицы на поверхности не по реальной проекционной математике:
- Для **плоскости** (строка 692): `[worldX * 0.1, worldY * 0.1, 0]` — произвольный масштаб, не связанный с реальной точкой проекции.
- Для **цилиндра/конуса**: используются `lat`/`lon` напрямую как локальные координаты, а не через `cylinderLocalEnd`/функции конуса.

Частицы не соответствуют тому, куда реально проецируются точки глобуса.

**Как исправить:** использовать `projectToAuxWorld` или эквивалентную математику для вычисления реальной точки посадки каждой частицы.

---

### 2.6 Тепловая карта не отражает реальное искажение проекции

**Файл:** `src/components/Map2D.tsx:36-62`

`HeatmapOverlay` раскрашивает ячейки на основе `t = 1 - cos(lat) / 1.2`, что зависит **только от широты**, а не от реального искажения площади/угла/масштаба текущей проекции. Тепловая карта одинакова для всех проекций.

**Как исправить:** использовать `computeAreaDistortion` для каждой ячейки (или аналогичную метрику) с учётом текущей проекции.

---

### 2.7 Лазерное кольцо: проекция на плоскость — заглушка

**Файл:** `src/utils/auxSurfaceGeometry.ts:744-745`

```ts
projectedPoints.push(auxPointToWorld(surface, [g[0] * 0.1, g[1] * 0.1, 0]));
```

«Спроецированное» кольцо на плоскости — просто координаты глобуса, сжатые в 10 раз. Никакой реальной проекционной математики.

**Как исправить:** вычислять реальную проекцию точек кольца на вспомогательную поверхность через `projectToAuxWorld`.

## 3. Технический долг и архитектурные проблемы

### 3.1 `variant` опционален, но не должен быть

**Файл:** `src/store/useAppStore.ts:53`

```ts
variant?: ProjectionVariant;
```

После инициализации (`defaultParamsForFamily`) или вызова `setVariant`/`setFamily` variant **всегда** определён. Опциональность порождает лишние проверки `variant ?? defaultVariant(family)` в десятке мест и риск undefined на граничных путях.

**Как исправить:** сделать `variant: ProjectionVariant` (обязательным), инициализировать всегда. Это безопасно, т.к. store создаётся через `defaultParamsForFamily`.

---

### 3.2 `setFamily` не сохраняет пользовательские настройки параметров

**Файл:** `src/store/useAppStore.ts:268`

```ts
setFamily: (family) => set({ ...defaultParamsForFamily(family) }),
```

Сброс ВСЕХ параметров (включая `lambda0`, `phiOrigin`, `scaleFactor`, `gamma`) при смене семейства. Пользователь теряет все настройки. Более дружественное поведение: сохранять общие параметры (`lambda0`, `phiOrigin`, `gamma`) и сбрасывать только семейство-специфичные.

**Как исправить:** копировать пересекающиеся параметры из текущего состояния.

---

### 3.3 Мёртвый код: `coneAxialHeight` задокументирован, но экспортирован без причины

**Файл:** `src/utils/auxSurfaceGeometry.ts:409`

`coneAxialHeight` — чистая функция, экспортирована, используется только внутри того же модуля. Экспорт не нужен, если нет внешних потребителей. (Проверить тесты: используется в `auxSurfaceGeometry.test.ts`? Если нет — убрать экспорт.)

---

### 3.4 `MAP_SCALE = 100` и `VIEW_CENTER` жёстко зашиты, но переопределяются `fitProjectionToView`

**Файл:** `src/utils/projectionMapper.ts:228-230`, `src/utils/projectionMapper.ts:436-449`

`getD3Projection` задаёт фиксированный `scale(100)` и `translate(400, 300)`, а затем `Map2D` вызывает `fitProjectionToView`, который ПЕРЕЗАПИСЫВАЕТ и scale, и translate через `fitExtent`. Константы `MAP_SCALE` и `VIEW_CENTER_*` используются только в 3D-математике лучей (`worldPerPixel`, вычисление `cy`), но не влияют на фактическое 2D отображение. Это создаёт путаницу.

**Как исправить:** задокументировать, что эти константы — «канонический масштаб» только для 3D-лучей, а 2D всегда переопределяется через `fitProjectionToView`. Или разделить на `CANONICAL_SCALE` и `CANONICAL_CENTER`.

---

### 3.5 `useProjectionParams` возвращает новый объект при любом изменении любого поля проекции

**Файл:** `src/store/selectors.ts:5-32`

Селектор возвращает ВСЕ параметры проекции как один объект. Изменение `rulerMode` (состояние линейки) вызывает пересоздание объекта `ProjectionParams`, что триггерит перерасчёт всех `useMemo`, зависимых от `params`. Поля линейки (`rulerMode`, `rulerPoint1`, `rulerPoint2`) не должны быть частью `ProjectionParams` — это чисто UI-состояние.

**Как исправить:** вынести `rulerMode`, `rulerPoint1`, `rulerPoint2` из `ProjectionParams` в отдельный интерфейс и селектор.

---

### 3.6 Тест документации статически ссылается на каждый файл

**Файл:** `src/__tests__/docsConsistency.test.ts`

Тест жёстко импортирует `AGENTS.md?raw`, `BRD.md?raw`, `new_spec.md?raw` и содержит захардкоженный список `srcFiles`. При добавлении/удалении любого файла нужно обновлять тест. Лучше использовать `import.meta.glob` для динамического сканирования.

**Как исправить:** `const srcFiles = import.meta.glob('../**/*.{ts,tsx}', { eager: true })`.

---

### 3.7 `loadGeoData` мутирует скрытое поле `_geoToken` через cast к `any`

**Файл:** `src/store/useAppStore.ts:295-296`

```ts
const token = (useAppStore.getState() as AppState & { _geoToken?: number })._geoToken ?? 0;
```

Поле `_geoToken` не объявлено в интерфейсе `AppState`, доступ через cast. Хрупко, не типобезопасно.

**Как исправить:** добавить `_geoToken` как приватное поле стора (Zustand позволяет хранить не-экспортируемые поля через `create<AppState & { _geoToken: number }>`).

## 4. Ошибки данных и конфигурации

### 4.1 Фиктивные EPSG-коды

**Файл:** `src/constants/epsgPresets.ts`

| Код | Реальность |
|-----|-----------|
| `EPSG:9820b` | Не существует. Код `9820` — это «Lambert Azimuthal Equal Area», не «Stereographic (South)». |
| `EPSG:54001c` | Не существует. `54001` — ESRI-код для «World Equidistant Conic», не «Azimuthal Equidistant». |
| `EPSG:54004` | ESRI-код, а не EPSG (ESRI:54004 = World Mercator). В пресете это «Бергман» через equirectangular+equalArea — неверно. |
| `EPSG:54006` | ESRI-код для Equal Area Cylindrical, а не «Бальтасар». |
| `EPSG:54007` | ESRI:54007 = World Sinusoidal, а не «Крастер». |
| `EPSG:54008` | ESRI:54008 = World Mollweide, а не «Хобо-Дайер». |
| `EPSG:54009` | ESRI:54009 = World Eckert V, а не «Тристан-Эдвардс». |

Все эти пресеты используют вариант `equirectangular` с разными `distortion`/`phiOrigin`, что даёт цилиндрическую проекцию, но НЕ ту, что указана в названии. Это вводит пользователя в заблуждение.

**Как исправить:** либо убрать эти пресеты (они не соответствуют заявленным проекциям), либо переименовать с корректными названиями, либо вынести в отдельную категорию «вариации стандартной параллели».

---

### 4.2 `EPSG:53010` (Галль-Петерс) — невалидный код

**Файл:** `src/constants/epsgPresets.ts:18`

Код `53010` не является стандартным EPSG-кодом. Это частный код из одной ГИС-системы. Правильных EPSG для Gall-Peters не существует.

## 5. Визуализационные методы-заглушки

Несколько методов визуализации в 3D — по сути заглушки, слабо или никак не связанные с реальной геометрией проекции:

| Метод | Компонент | Проблема |
|-------|-----------|----------|
| `normals` | `PerpendicularNormals.tsx` | Нормали не упираются в реальную поверхность (п. 2.4) |
| `particles` | `ParticleTransfer.tsx` | Частицы не соответствуют реальным точкам проекции (п. 2.5) |
| `magnetic` | `MagneticField.tsx` | Линии — чистая синусоида над глобусом, не связаны с поверхностью |
| `peel` | `PeelOff.tsx` | Просто пульсирующая сфера, не разворачивается в поверхность |
| `wave` | `WaveProjection.tsx` | Расширяющаяся сфера, никак не связана с проекцией |
| `laser` | `LaserScanner.tsx` | Проекция кольца на плоскость — заглушка (п. 2.7) |
| `construction` | `GeometricConstruction.tsx` | Статические линии: ось Y + три радиуса. Нет реального геометрического построения |
| `shadow` | `ShadowPlay.tsx` | Три статических луча с экватора. Не привязаны к источнику света проекции |

Из 8 методов только `laser` и `normals` имеют шанс стать информативными после исправления. Остальные 6 — декоративные, не выполняют образовательную функцию.

**Как исправить:** либо довести до ума (привязать к реальной геометрии), либо убрать из UI, оставив только работающие.

```ts
const secant = p.family === 'conic' ? p.stdParallel2 != null : p.scaleFactor !== 1;
```

Для **не**-конических проекций условие `scaleFactor !== 1` не означает «секущая поверхность». Для цилиндра `scaleFactor < 1` означает, что цилиндр пересекает глобус (секущий), но эта логика не универсальна.
