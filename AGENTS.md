# AGENTS.md

## Project status
Working MVP of «Carto-Space» — an interactive cartographic-projection simulator (educational tool showing the 3D Earth ↔ 2D map relationship). Client-side SPA only: **no backend, no external APIs**; all projection math runs in-browser. Product/legacy specs live in `docs/BRD.md` (business, Russian). The historical `docs/new_spec` / `docs/specification.md` files were never created — **this `AGENTS.md` is the authoritative implementation reference.** The app UI language must be Russian.

## Commands
Run **directly from the project directory** `/mnt/d/_projects/pet_project/map_project_browser`:
- `npm run dev` — Vite dev server
- `npm run build` — `tsc -b && vite build` (typecheck + production build)
- `npm run lint` — ESLint
- `npm run test` — Vitest (`vitest run`); `npm run test:watch` for watch mode
- `npm run test:coverage` — Vitest with V8 coverage report (writes to `coverage/`, git-ignored); local-only, no CI thresholds / no Codecov upload. The 3D scene / viz-renderer components and pure style/token modules are excluded (per §9.3 they're intentionally untested), so the report reflects only the actually-exercised code.
- `npm run preview` — preview the built app

Typecheck is part of `build` (`tsc -b`); there is no separate `typecheck` script. `lint` runs before `build` in CI, so lint errors fail the build there.

## Dev workspace / DrvFS workaround (CRITICAL)
`/mnt/d` is a Windows-mounted drive (9P/DrvFS). `npm install` fails there with `ENOTDIR` on `mkdir node_modules`, and a corrupted `node_modules` dentry cannot be removed from inside the container. We keep a real `node_modules` on the **native Linux filesystem** and symlink it into the project:
- Native home for deps lives on the **persistent** WSL filesystem (NOT `/tmp`, which is wiped on every reboot): `~/mbp-deps/node_modules`, created via `npm ci` inside `~/mbp-deps` (that dir also holds `package.json` + `package-lock.json`). Use the WSL home of whichever user runs the build — typically `/home/<user>/mbp-deps`.
- In the project dir, `node_modules` is a symlink → `~/mbp-deps/node_modules` (the symlink itself lives on the Windows disk under `/mnt/d`, so it survives reboots too). `eslint.config.js` is a real native copy (or symlink). No other source/config symlinks are needed.
- `vite.config.ts` sets `server.watch.usePolling` because DrvFS emits no `inotify` events, so Vite's watcher otherwise never sees edits under `/mnt/d` (HMR won't fire). No `preserveSymlinks` is needed — sources are local.

Because the native deps and the project symlink are both persistent, **no setup is needed after a reboot** — just `npm run dev` from WSL. The one-time setup (run once from WSL): `H=~/mbp-deps; mkdir -p "$H" && cp package.json package-lock.json "$H"/ && cd "$H" && npm ci`, then `ln -sfn "$H/node_modules" /mnt/d/_projects/pet_project/map_project_browser/node_modules`. Only re-run this if the symlink/target is ever deleted. **Do NOT run `npm install`/`npm ci` inside `/mnt/d`.**

## Architecture (how it is wired)
- **Three projection families** by the developable surface: `cylindrical`, `conic`, `azimuthalPerspective`. Cylindrical/conic have developable aux surfaces (cylinder/cone) shown in 3D; `azimuthalPerspective` uses a tangent projection plane (the light-source perspective family: gnomonic / stereographic / orthographic — the projection IS the ray construction from the light position). Each family shows its projection via the rays from the light source through the globe onto the surface; the 2D map is the unrolled surface.
- **7 named variants** across the three families:
  - `cylindrical`: `equirectangular`, `mercator`
  - `conic`: `lambertConformal`, `albers` (rays from the cone apex are drawn for the conic family too)
  - `azimuthalPerspective`: `gnomonic`, `stereographic`, `orthographic`
  - Removed in the simplification refactor: `transverseMercator` (+ UTM zones), `obliqueMercator` (+ SOM orbital params), `equidistantConic`, `verticalPerspective` / `tiltedPerspective` (satellite), the whole `azimuthalMath` family (`lambertAzimuthalEqualArea`, `azimuthalEquidistant`), the EPSG catalog, the k₀ slider, and the old legacy variants `miller`, `gallPeters`, `lambertCylEqualArea`, `polyconic`. **Do not reintroduce them.**
- Single Zustand store `src/store/useAppStore.ts` is the **only** source of truth; UI / 2D / 3D components only read from it or call its actions (`setParam`, `setVariant`, `setShowTissot`, `setFamily`, `resetParams`, `loadGeoData`, and the many `setX` helpers). `setFamily(family)` switches the family **and resets to the family-default variant** (cylindrical → `mercator`, conic → `lambertConformal`, azimuthalPerspective → `gnomonic`), which in turn sets the appropriate `distortion`, `azLight`, and locked param values. `setVariant(variant)` switches the named projection variant within the current family, setting `family`, `distortion`, `azLight`, and default params accordingly. `resetParams()` resets all params to the **current** variant's defaults without switching the projection (the variant / family stay untouched — e.g. a reset on `albers` keeps `albers` and its `equalArea` distortion).
- `src/utils/projectionMapper.ts` exports `getD3Projection(state)`, `computeAreaDistortion(params)`, `fitProjectionToView(proj, w, h, margin)`, `isPointerOverGlobe(path, x, y)`, `makeFrameRotation(lambda0, phiOrigin)` (the spherical roll of the Earth inside the static cylinder, = d3 `geoRotation([-lambda0, -phiOrigin])`, with `.invert()` for the reverse mapping), the `FIT_SPHERE` constant, and the local-area helper `localAreaScale(proj, lon, lat, d)` (px² per steradian at a point, or null off-projection / on a discontinuity). It maps (`family` × `distortion` × `azLight`) → a D3 projection; for conic / azimuthal it applies `proj.rotate([-(lambda0), -phiOrigin, rotZ]).scale(MAP_SCALE * scaleFactor).translate([VIEW_CENTER_X + falseEasting, VIEW_CENTER_Y + falseNorthing])` (constants from `constants/geometry.ts`; `MAP_SCALE=100`, `VIEW_CENTER_X=400`, `VIEW_CENTER_Y=300`). Note the **negative** rotation signs. The azimuthal light-source mapping: `center` → `geoGnomonic`, `antipode` → `geoStereographic`, `infinity` → `geoOrthographic`. For the **cylindrical** family `gamma` is **ignored** (fixed at 0), and the D3 projection object is the STATIC drum frame: it carries NO rotation at all (`rotate([0, 0, 0])`) whatever the sliders do. Долгота/Параллель instead ROLL the geography INSIDE the tube — a true spherical rotation (`makeFrameRotation`) applied to the input coordinates BEFORE the projection sees them (data helpers in `utils/geoBandClip.ts`: `rotateFeatureCollection`, `rotatePolygon`, `normalizeLon`). This makes the flat map an HONEST projection: the chosen central point (λ₀, φ₀) always lands on the middle row with the LEAST distortion, and content farther away stretches toward the window edges (south pole centred ⇒ the pole is nearly true-scale while the former equator, now ±90° away, is stretched enormously) — the map never merely slides. The roll mirrors the 3D coastline matrix `projectionRotationMatrix(-lambda0, -phiOrigin, 0)` exactly (a physics test locks the agreement), so both views show the same rolled Earth. The 3D tube is STATIC too (upright, identity orientation): Долгота/Параллель roll only the continents inside it, and the ray fan is a STATIC apparatus — built from the un-rotated, un-slid projection and anchored to the grid's central meridian, it never moves with the sliders. `precision(0)` is always on for the cylindrical family: the drum's graduation rows stay ruler-straight horizontal lines (no "egg"). `fitProjectionToView` overrides scale/translate to fit the 2D map to its container (the fixed `scale(100)` is only used by the 3D ray math). For the conic and azimuthal families it fits a **clipped ±85° sphere** (`FIT_SPHERE`) to the viewport, NOT a full `{type:'Sphere'}` (the pole maps to infinity for some projections, collapsing the scale). For the **cylindrical** family the 2D map follows the static-drum model. The CYLINDER IS STATIC — upright, never tilted or spun; its graduation grid (straight horizontal parallels, vertical meridians, poles at the window edges) is FIXED to it. Map2D builds exactly ONE fitted D3 projection per render and drives EVERY vector layer (graticule, coastlines, borders, Tissot circles, intersection rings, cut line) through it: for the cylindrical family `getD3Projection` bakes NO rotation into the projection whatever the sliders do, so the grid layer is automatically the static drum frame while the geography layers arrive pre-rolled. For the conic / azimuthal families that same single projection carries the rotation, so the grid follows Долгота/Параллель together with the coastlines (a regression test locks both behaviours). The GEOGRAPHY LAYER (continents, borders, Tissot circles) IS RE-PROJECTED on every slider move: Долгота/Параллель roll it via `makeFrameRotation` (`rotateFeatureCollection` / `rotatePolygon` apply the rotation to every coordinate; Map2D does this before drawing), so the continents genuinely bend around the drum — geographic meridians/parallels curve when the pole is centred, while the drum's own ruler rows under them stay straight. The VERTICAL COORDINATE STAYS PERIODIC in the drum frame: frame latitude is FOLDED into the band ±`CLIP_LAT` with period 2·`CLIP_LAT` (symmetric modulo — the edges stay on their own sides), so content past a drum rim belongs to the opposite one (scrolling past a rim would wrap to the opposite side). Geography data is PRE-ROTATED into the drum frame and THEN pre-cut at ±`CLIP_LAT` (`geoBandClip.cutFeatureCollectionToBand`, applied in Map2D after the rotation) so no ring ever crosses the wrap seam. Both layers share one analytic band fit (scale from the ±`CLIP_LAT` band rectangle — constant window size for every slider state; the drum never zooms and never slides), and each layer is clipped by `clipExtent` to the fixed viewport frame set AFTER the final translate (d3 clipExtent works in screen pixels but must be applied last — setting it before a later translate desynchronises it). Map2D draws exactly ONE copy of every layer through a single fitted projection — the space above and below the finite band stays empty background (the old three-stacked-copies "endless tape" read as a rendering bug and was removed). The raw height law is clamped to ±`CLAMP_LAT` (just beyond the band edge) to keep Mercator finite. The `variant` field selects the named projection. For the **cylindrical** family the diameter (`scaleFactor`) is the cylinder radius R·`scaleFactor`; the cylinder meets the globe at the contact parallels ±arccos(`scaleFactor`). Latitudes beyond ±`CLIP_LAT` (from the cylinder axis, in the local frame) are clamped so the tube is **finite**. `gamma` (stored in **degrees** in the store) is editable only for the **azimuthal** family (the in-plane rotation of the map around the touch point); for cylindrical and conic it is fixed at 0.
- 2D `src/components/Map2D.tsx`: responsive SVG (measures its container via `ResizeObserver`) whose projection is fitted with `fitProjectionToView`; graticule (toggled by the **Сетка** button), coastlines from `land50GeoJson` (≥50m detail), optional country-border layer from `countriesGeoJson`, and optional Tissot indicatrices via `d3Geo.geoCircle().radius(5)` on a 30° grid. For the cylindrical family the geography layers (land, borders, Tissot circles) are pre-rotated into the drum frame with `makeFrameRotation` + `geoBandClip.rotateFeatureCollection` / `rotatePolygon` and then band-cut, so they genuinely bend around the static drum; the hover cursor position is un-rolled back to geographic lon/lat through the rotation's `.invert()` before it lands in the shared store. The globe always fills the viewport (with a small uniform margin) for every `scaleFactor`, fitted to the container preserving the projection's own aspect ratio (`object-fit: contain`). The cylinder diameter (cylindrical) is therefore NOT visible as a 2D size change — it shows through the map's aspect and through the 3D / Tissot intersection rings and the `Искажение площади` number. The **Индикатрисы Тиссо**, **Сетка**, **Детализация карты** and **Границы стран** buttons are always visible together as a single horizontal row in the map's top-right corner (plus the intersection-ring, hover-ray and exact-parameters buttons in the same row). The **Сетка** button toggles the graticule **on the 2D map only** — the 3D globe never draws a graticule (its globe surface shows only coastlines). When detail is off, `Map2D` draws the lightweight 110m `geoJsonData` land with 110m borders (`countries110GeoJson`) instead of the 50m datasets. The map's **bottom-right corner** shows a small glass label `Искажение площади: NN%` — the area-weighted area distortion, computed by `computeAreaDistortion` (in `projectionMapper.ts`): it samples local area-scale factors on a fine lon/lat grid and reports the mean relative area excess (equal-area projections → ~0%). The 100% reference is the area scale **at the standard parallel (where true scale = 1)**. The map's **bottom-left corner** carries a neon link to the Stepik course «Геопространственный анализ данных на Python» (https://stepik.org/a/258792).
- 3D scene `src/components/GlobeScene.tsx` composes the thin components (all flat under `components/`, no `Scene3D/` subfolder): `Globe.tsx` (transparent dark sphere with neon-blue **3D-line** coastlines — no graticule: the globe never draws one, the **Сетка** button affects only the 2D map; NOT the `CanvasTexture`/orthographic variant from the old spec; the coastline GEOGRAPHY LAYER rolls with Долгота/Параллель via the rigid matrix `projectionRotationMatrix(-lambda0, -phiOrigin, 0)` while the shell stays fixed), `AuxSurface.tsx` (fully transparent neon-orange **wireframe** of the developable surface — its own meridians + parallels; cylinder for cylindrical, cone for conic, plane for azimuthal), `IntersectionDisks.tsx` (hollow **white** rings marking the **actual** intersection of the aux surface with the globe — 0, 1 or 2 circles; the component renders nothing when the surface does not touch the globe), `LightSource.tsx` (yellow lamp at the azimuthal light position or at the conic cone apex), `Rays.tsx` (the single projection visualization — rays from the light through the globe points onto the surface), plus `CutLine.tsx` (the white surface seam/cut line) and `TouchPointPin.tsx` (the yellow azimuthal touch-point pin). The white apparatus lines — `IntersectionDisks` + `CutLine` — render ONLY while the **Линии пересечения и линия разреза** toggle (`showIntersection`) is on; the SAME flag drives the matching white line layers on the 2D map (default off: no lines in either view until enabled). `GlobeScene` computes the developable-surface geometry once (`computeAuxSurfaceParams`, memoized on the projection params) and passes the resulting `surface` object down so all consumers share one computation and can never drift apart. The azimuthal aux-plane wireframe rotates its grid points directly by the tangent-basis quaternion so its orientation is always correct. `GlobeScene` adds `OrbitControls` (from `@react-three/drei`, `makeDefault`, pan disabled) so the user can rotate/zoom the camera. The 2D map (`Map2D.tsx`) and the 3D globe share a **hover linkage**: hovering either view reads the (lon, lat) under the cursor into the store's `hoverLonLat` and the other view draws a matching yellow marker; the 3D marker is placed through the SAME coastline roll matrix, so it rides the visibly rotated continents instead of the un-rotated geographic position. Hovering the **2D map** (with `showHoverRay` on) draws the cursor projection ray via `projectToAuxWorld`. Hovering the **3D globe** does **not** draw the ray or the marker (the hover highlight is driven solely by the 2D map).
- `src/utils/auxSurfaceGeometry.ts` is the **single source of truth** for all 3D geometry: `computeAuxSurfaceParams`, `computeAuxGraticule`, `computeAuxSphereIntersections` (the real aux-surface↔globe intersection circles, in 3D world coords) and `computeAuxSphereIntersectionsLonLat` (the same circles projected back to lon/lat for the 2D map's `showIntersection` layer), `auxPointToWorld` (the single world-transform for the aux surface, shared by `AuxSurface` and the rays so they can never drift), `computeCentralMeridianRays` (the central-meridian ray fan) and `projectToAuxWorld` (the per-point ray used by the hover demo; for the cylindrical family the hovered point is FIRST rolled into the drum frame via `makeFrameRotation`, so the landing follows the rotated continent exactly like the flat map draws it), `computeTangentBasis`, `lonLatToVec3` (`RADIUS = 10`) and its inverse `vec3ToLonLat` (used by `GlobeScene` to read the cursor's lon/lat off the 3D globe for the hover linkage). Surface, ring, and rays derive from the same math so they can never drift apart. (Replaces the old `rayGeometry.ts`.) It also exposes the cut-line math `computeCutLine` with its lon/lat wrapper `computeCutLineLonLat` (the 2D map's seam layer — the same white line the 3D `CutLine` draws; empty for the azimuthal plane) and the vector helpers `vec3Distance`, `vec3Normalize`. `computeCone(phi1, phi2, radius, scaleFactor)` supports both **tangent** (φ1 = φ2) and **secant** (φ1 ≠ φ2, same hemisphere) cones; the cone sits in the **signed** hemisphere of `phiOrigin` (so a southern `phiOrigin` yields a south-pointing cone) while the parallel *magnitude* uses the equatorial `30°` fallback on `|phiOrigin|`. `gamma` (stored in **degrees** in the store, editable only for azimuthal) is converted to radians inside this module and inside `AuxSurface.tsx` (Three.js rotations are radians), so the rays and the wireframe stay aligned. `computeCentralMeridianRays` honours the azimuthal `azLight` modes (`center` → rays from the globe centre (gnomonic), `antipode` → rays from the antipode (stereographic), `infinity` → parallel orthographic beams arriving along the **radial** normal). `computeAuxSurfaceParams` takes the full projection descriptor. The cylinder always passes through the globe centre and touches it (secant, radius `scaleFactor`·R). Its axis is POLAR and STATIC (upright, identity orientation — it never tilts with φ₀; the geography rolls inside it), matching the flat map's static drum. `clampLocalToSurface(surface, p)` then clamps every ray endpoint to the rendered surface's finite extent so a ray can never fly into empty space (exposed via `computeConicRayEnd(..., clamp=true)` for tests). `AuxSurface.tsx` calls `computeAuxSurfaceParams` with the same full param set so the wireframe and the rays share identical sizing, and `Rays.tsx` draws the hover ray as a polyline `start→globe→end` so the yellow globe marker lies exactly on the beam.
- The rays (`Rays.tsx`) are the **single** projection visualization in the 3D scene: a yellow fan from the light source (globe centre for cylindrical, cone apex for conic, azimuthal light position for azimuthal) through the globe points onto the aux surface, plus the cursor hover ray. The decorative "visualization methods" (normals, particles, magnetic, peel, wave, laser, construction, shadow) were removed in the simplification refactor. `CutLine.tsx` draws the developable-surface cut/peel line; `TouchPointPin.tsx` marks the azimuthal touch point. The rays are always shown (no toggle).
- `src/utils/tissot.ts` builds the Tissot indicatrices for the 2D `Map2D` overlay: `computeTissotCircles(density)` returns an array of 5°-radius spherical circles (`d3Geo.geoCircle().radius(5)`) on a `density`-degree lon/lat grid (default 30°), staggered by half a step on every other latitude row so the pattern is even. `Map2D` passes the store's `graticuleStep` as `density` so the indicatrices line up with the visible graticule. Used only when `showTissot` is on.
- `src/constants/designTokens.ts` exports the shared palette `NEON_BLUE` / `NEON_ORANGE` / `NEON_YELLOW` / `NEON_WHITE` / `BG`; both 2D and 3D components import it instead of hard-coding the hex values. `src/constants/geometry.ts` holds shared numeric constants (`MAP_SCALE`, `VIEW_CENTER_X/Y`, `CLIP_LAT`, `FIT_MARGIN`, `RADIUS`, `RAY_COUNT`, aux-surface factors, `STD_PARALLEL_MIN_ABS` / `STD_PARALLEL_FALLBACK`) — single source so magic numbers never drift between the 2D map and the 3D scene.
- `src/store/selectors.ts` exposes `useProjectionParams()` (a memoized `ProjectionParams` slice) so consumers read the projection state as one object instead of subscribing to every field. `GlobeScene` and `Map2D` use it.
- `src/components/ui/` holds shared styling extracted from `ControlPanel.tsx`: `icons.tsx` (all SVG icons), `styles.ts`, `labels.ts`, and the reusable controls `ParamSlider.tsx` (labelled range slider with value readout + disabled/locked state) and `PresetChips.tsx` (a row of active/inactive preset buttons). Keep cross-component UI here, not in a component file, to avoid `react-refresh` export warnings.
- `src/components/ProjectionHeader.tsx`: the slim top header of the left column (rendered by `App.tsx` above the scrolling `ControlPanel`) — **one glass block filling the whole area** (`border-neon-blue/50` + `bg-panel-bg`, rounded, like other panel elements), split by a **vertical** `NEON_DIVIDER` line from top to bottom into two zones: the wide left zone is the projection **dropdown** — a custom neon-glass control (a button showing the current variant, the family conveyed by the family icon, plus a chevron) that opens a glass **listbox** panel below the header listing all 7 projections grouped by family headers; keyboard navigation (↑/↓, Enter, Esc) and click-outside-to-close are wired up; picking an option calls `setVariant(variant)`. The narrow right zone resets the parameters. Unit-tested in `ProjectionHeader.test.tsx`.
- `src/components/GlobeScene.tsx` passes the computed `surface` object down to `AuxSurface`, `IntersectionDisks` and `LightSource`, so all three share one computation and can never drift apart. Every family renders rays: cylindrical/conic from the centre/apex, azimuthal from the light position.
- `src/components/ProjectionSummary.tsx`: the read-only **Геодетическая сводка** (Geodetic Summary) modal opened by the **ℹ️ Точные параметры** button in `Map2D.tsx`'s map toolbar (top-right corner, same plain-icon style as the other map buttons); lists λ₀, φ₀, φ₁, φ₂ (conic), scale, γ (azimuthal), hemisphere (conic), `falseEasting`, `falseNorthing` and the computed projection class.
- `src/components/ErrorBoundary.tsx`: a React class error boundary (the only way to catch a child's render-time throw) wrapping `GlobeScene` in `App.tsx`. ## Store shape (verified in code)
ProjectionParams (the param slice of the store, type `ProjectionParams`):
```ts
variant: ProjectionVariant;  // named projection variant — determines family/distortion/azLight
family: 'cylindrical' | 'conic' | 'azimuthalPerspective';
distortion: 'conformal' | 'equalArea' | 'equidistant';
lambda0: number;       // -180...180  central meridian
phiOrigin: number;     // -90...90    central latitude
scaleFactor: number;   // 0.9...1.1 (conic/azimuthal); 0.5...1.0 cylindrical (1.0 = cylinder diameter = Earth's, 0.5 = half)
falseEasting: number;  // -1000...1000
falseNorthing: number; // -1000...1000
gamma: number;         // -180...180  tilt / in-plane rotation; editable only for azimuthal
stdParallel2: number | null;          // φ2; null = tangent surface (single standard parallel)
azLight: 'center' | 'antipode' | 'infinity';   // azimuthal light-source mode

// Cone hemisphere (north / south)
coneHemisphere: 'north' | 'south';
```
Non-param state (also on the store):
```ts
showTissot: boolean;
showBorders: boolean;                 // 2D country-border layer toggle (default false)
showIntersection: boolean;            // white apparatus lines (aux-surface∩globe rings + seam/cut line) in BOTH the 2D map and the 3D scene (default false)
geoJsonData: FeatureCollection | null;      // land-110m, source for the 3D globe
land50GeoJson: FeatureCollection | null;    // land-50m, 2D base map
countriesGeoJson: FeatureCollection | null; // countries-50m, 2D border layer (detailed mode)
countries110GeoJson: FeatureCollection | null; // countries-110m, 2D border layer (lightweight mode)
detailedMap: boolean;                       // 2D map detail toggle (default false → lightweight 110m land + 110m borders; true → 50m land + 50m borders)
geoLoading: boolean;                        // true while loadGeoData fetches the bundled geodata
geoDataError: string | null;                // friendly Russian message set when BOTH the 110m and 50m land fetches fail (null otherwise); Map2D shows it in the empty-map overlay so the user knows to reload
hoverLonLat: [number, number] | null;  // hovered (lon, lat), shared so the other view mirrors the highlight
hoverSource: 'globe' | 'map' | null;   // which view set hoverLonLat (ray drawn only for 'map')
showHoverRay: boolean;                 // cursor projection ray in the 3D scene, shown only while the 2D map is hovered (default false)

// Non-parametric visualization / interaction state
graticuleStep: 1 | 5 | 10 | 15 | 30;
showGraticule: boolean;
```
Map data is bundled locally (no runtime/external API, per spec): `public/world-110m.topojson` (Natural Earth 1:110m land, used by the 3D globe), plus `public/land-50m.json` and `public/countries-50m.json` (1:50m, used by the 2D `Map2D`). All three files are **TopoJSON** (`{type:'Topology'}` with `objects.land` / `objects.countries`); despite the `.json` extension they are parsed via `topojson-client`'s `feature()`, not fetched as GeoJSON. `loadGeoData` fetches all three in parallel and stores them separately; a failed fetch for one file does not abort the others. A monotonic `_geoToken` discards stale results if a newer fetch starts before an older one resolves (so a fast remount can't overwrite fresh data with stale data). If BOTH the 110m and 50m land fetches fail the 2D map has nothing to render and `geoDataError` is set to a friendly Russian message («Не удалось загрузить карту. Проверьте подключение к интернету и перезагрузите страницу.»); `Map2D` shows it in its empty-map overlay (no retry button — the user reloads the page). A partial failure (any single file) stays silent because the surviving layers still produce a usable map. As of the 110m-borders change it also loads `public/countries-110m.json` (Natural Earth 1:110m Admin 0) into `countries110GeoJson`. The lightweight 2D map now draws 110m borders (`countries110GeoJson`), while the detailed map keeps 50m borders (`countriesGeoJson`); the **Границы стран** button is always visible and toggles a real border layer in both lightweight and detailed modes. `isEllipsoid` was removed — the model is **spherical** (D3 projections are spherical too; true ellipsoidal support is out of scope).

## Hard rules / conventions (from spec, enforced in code)
- Strict TypeScript: no `any` in component props; type the TopoJSON `FeatureCollection`.
- Wrap D3 projection / `pathGenerator` / ray math in `useMemo` — real-time perf requirement, never recompute per frame.
- All controls are always visible — when a parameter is locked by the selected projection variant it shows as **disabled** (not hidden), with `🔒` prefix and the locked value. The visual/physical params each have a dedicated control, labeled with the **physical terms** of the projection; controls are **context-dependent** (some shown only for certain variants, e.g. parallel 2 for secant cones, north/south hemisphere for conic, touch-point presets for azimuthal). The **Тип искажения** (`distortion`) is set implicitly via the variant dropdown. The **ℹ️ Точные параметры** button lives in the 2D map's top-right toolbar (same plain-icon style as the other map buttons) and opens a read-only Geodetic Summary **modal** listing λ₀, φ₀, φ₁, φ₂, scale, γ, and the computed projection class. ## Gotchas an agent will likely miss
- `falseEasting` / `falseNorthing` exist in the store and projection math but have **no sliders in the UI** (only `lambda0`, `phiOrigin`, `scaleFactor`, `stdParallel2`, `gamma` [azimuthal], `coneHemisphere` are exposed). Don't assume they're wired to controls.
- The four family buttons in `ControlPanel` are a single segmented control (overlapping borders via `-ml-px`, `z-10` on the active one) — keep the segmented look when editing.
- The projection dropdown is a **custom** neon-glass listbox (a native `<select>` popup is OS-rendered and cannot match the app style) — keep the glass look (`bg-panel-bg` + `border-neon-blue/50`), the family headers, the ↑/↓ + Enter + Esc keyboard handling and the click-outside close when editing.

- Map2D builds exactly ONE fitted D3 path generator per render for ALL layers. An earlier version built a second one for the graticule/apparatus lines whose memo deps omitted λ₀/φ₀/γ, freezing the grid on the conic / azimuthal maps while the coastlines moved; a regression test locks the grid following Долгота there (and staying static on cylindrical). Do not split the generators again.
- `fitProjectionToView(proj, w, h, margin)` no longer takes a fit-target argument (nothing ever passed one), and `computeCutLine(surface, numPoints)` dropped its ignored `_lambda0` / `_family` arguments.
- The 3D globe used to render HORIZONTALLY MIRRORED continents: `projectionRotationMatrix` built its third column from the (lon 90°) basis image without the minus sign that the world frame's −Z longitude convention requires (det = −1, a reflection). Fixed — the matrix is now a proper rotation (det = +1, locked by a physics test). Do not remove the minus.
- The intersection rings were neon-green (`#00ff66`) and the cut line neon-red (`#ff3333`), both always drawn in 3D. They were unified to `NEON_WHITE`, placed under the **Линии пересечения и линия разреза** toggle together with their 2D counterparts, and the unused `NEON_GREEN` / `NEON_RED` tokens were deleted from `designTokens.ts`. Do not reintroduce them.
- The 2D cylindrical map used to stack THREE tile copies one band height apart (`createProjectionTiles` in `projectionMapper.ts`) into an "endless vertical tape". On the short, wide equirectangular band the two extra copies filled the leftover rows and read as a rendering bug (three flattened worlds stacked vertically). The helper was deleted: Map2D now draws exactly ONE copy of every layer through a single fitted projection and spare space stays empty background. The periodic fold law itself stays (content past a rim belongs to the opposite one). Do not reintroduce the tape.

## CI
`.github/workflows/ci.yml` runs `npm ci` → `lint` → `build` → `test` on push/PR (GitHub-hosted Linux, no DrvFS quirks). Tests run with `npm run test` (Vitest, jsdom). `src/__tests__/docsConsistency.test.ts` is the doc↔code guard: it fails the build if AGENTS.md / `docs/BRD.md` drift from the real source (broken `src/...` references, missing component files, dropped store fields/exports, or wrong constants). Keep that test in sync whenever you rename a file, drop an export, or change a documented constant. In addition `src/__tests__/physics.test.ts` is the large **physics** suite that locks in the geometric invariants: globe↔map projection round-trips and central-meridian x-centering for every `family`×`distortion`, the "globe point → map point" ray linkage (each ray's landing round-trips through `auxPointToWorld`), Tissot indicatrix behaviour, aux-surface↔globe intersection counts, area-distortion invariants, and globe-geometry sanity. When you change `auxSurfaceGeometry.ts`, `projectionMapper.ts`, or `tissot.ts`, extend these tests rather than loosening tolerances.
