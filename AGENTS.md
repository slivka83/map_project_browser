# AGENTS.md

## Project status
Working MVP of «Carto-Space» — an interactive cartographic-projection simulator (educational tool showing the 3D Earth ↔ 2D map relationship). Client-side SPA only: **no backend, no external APIs**; all projection math runs in-browser. Product/legacy specs live in `docs/BRD.md` (business, Russian). The historical `docs/new_spec` / `docs/specification.md` files were never created — **this `AGENTS.md` is the authoritative implementation reference.** The app UI language must be Russian.

## Commands
Run **directly from the project directory** `/mnt/d/_projects/pet_project/map_project_browser`:
- `npm run dev` — Vite dev server
- `npm run build` — `tsc -b && vite build` (typecheck + production build)
- `npm run lint` — ESLint
- `npm run test` — Vitest (`vitest run`); `npm run test:watch` for watch mode
- `npm run test:coverage` — Vitest with V8 coverage report (writes to `coverage/`, git-ignored); local-only, no CI thresholds / no Codecov upload. The 3D scene / viz-renderer components and pure style/token modules are excluded (per §9.3 they're intentionally untested), so the report reflects only the actually-exercised code.
- `npm run preview` — preview the built app

Typecheck is part of `build` (`tsc -b`); there is no separate `typecheck` script. `lint` runs before `build` in CI, so lint errors fail the build there.

## Dev workspace / DrvFS workaround (CRITICAL)
`/mnt/d` is a Windows-mounted drive (9P/DrvFS). `npm install` fails there with `ENOTDIR` on `mkdir node_modules`, and a corrupted `node_modules` dentry cannot be removed from inside the container. We keep a real `node_modules` on the **native Linux filesystem** and symlink it into the project:
- Native home for deps lives on the **persistent** WSL filesystem (NOT `/tmp`, which is wiped on every reboot): `~/mbp-deps/node_modules`, created via `npm ci` inside `~/mbp-deps` (that dir also holds `package.json` + `package-lock.json`). Use the WSL home of whichever user runs the build — typically `/home/<user>/mbp-deps`.
- In the project dir, `node_modules` is a symlink → `~/mbp-deps/node_modules` (the symlink itself lives on the Windows disk under `/mnt/d`, so it survives reboots too). `eslint.config.js` is a real native copy (or symlink). No other source/config symlinks are needed.
- `vite.config.ts` sets `server.watch.usePolling` because DrvFS emits no `inotify` events, so Vite's watcher otherwise never sees edits under `/mnt/d` (HMR won't fire). No `preserveSymlinks` is needed — sources are local.

Because the native deps and the project symlink are both persistent, **no setup is needed after a reboot** — just `npm run dev` from WSL. The one-time setup (run once from WSL): `H=~/mbp-deps; mkdir -p "$H" && cp package.json package-lock.json "$H"/ && cd "$H" && npm ci`, then `ln -sfn "$H/node_modules" /mnt/d/_projects/pet_project/map_project_browser/node_modules`. Only re-run this if the symlink/target is ever deleted. **Do NOT run `npm install`/`npm ci` inside `/mnt/d`.**

## Architecture (how it is wired)
- **Three projection families** by the developable surface: `cylindrical`, `conic`, `azimuthalPerspective`. Cylindrical/conic have developable aux surfaces (cylinder/cone) shown in 3D; `azimuthalPerspective` uses a tangent projection plane (the light-source perspective family: gnomonic / stereographic / orthographic — the projection IS the ray construction from the light position). Each family shows its projection via the rays from the light source through the globe onto the surface; the 2D map is the unrolled surface.
- **7 named variants** across the three families:
  - `cylindrical`: `equirectangular`, `mercator`
  - `conic`: `lambertConformal`, `albers` (rays from the cone apex are drawn for the conic family too)
  - `azimuthalPerspective`: `gnomonic`, `stereographic`, `orthographic`
  - Removed in the simplification refactor: `transverseMercator` (+ UTM zones), `obliqueMercator` (+ SOM orbital params), `equidistantConic`, `verticalPerspective` / `tiltedPerspective` (satellite), the whole `azimuthalMath` family (`lambertAzimuthalEqualArea`, `azimuthalEquidistant`), the EPSG catalog, the k₀ slider, and the old legacy variants `miller`, `gallPeters`, `lambertCylEqualArea`, `polyconic`. **Do not reintroduce them.**
- Single Zustand store `src/store/useAppStore.ts` is the **only** source of truth; UI / 2D / 3D components only read from it or call its actions (`setParam`, `setVariant`, `setShowTissot`, `setFamily`, `resetParams`, `loadGeoData`, and the many `setX` helpers). `setFamily(family)` switches the family **and resets to the family-default variant** (cylindrical → `mercator`, conic → `lambertConformal`, azimuthalPerspective → `gnomonic`), which in turn sets the appropriate `distortion`, `azLight`, and locked param values. `setVariant(variant)` switches the named projection variant within the current family, setting `family`, `distortion`, `azLight`, and default params accordingly. `resetParams()` resets all params to the **current** variant's defaults without switching the projection (the variant / family stay untouched — e.g. a reset on `albers` keeps `albers` and its `equalArea` distortion); it also bumps `_sceneResetToken`, and `GlobeScene` reacts by calling the orbit controls' reset so the 3D camera returns to its initial pose («Сбросить» restores the whole scene, not just the sliders).
- `src/utils/projectionMapper.ts` exports `getD3Projection(state)`, `computeAreaDistortion(params)`, `fitProjectionToView(proj, w, h, margin)`, `isPointerOverGlobe(path, x, y)`, `makeFrameRotation(lambda0, phiOrigin)` (the spherical roll of the Earth inside the static cylinder, = d3 `geoRotation([-lambda0, -phiOrigin])`, with `.invert()` for the reverse mapping), `makeGraticule(step, family)` (the 2D map's graticule: for the cylindrical family it is built EXPLICITLY with every line sampled every 5° and its extent pinned to the drum band ±`CLIP_LAT`, so the border rectangle coincides exactly with the map window — d3's own graticule is unusable there: its default outline follows the poles and folds under the fold law to a phantom inner rectangle, and even a pinned-extent d3 outline is emitted as degenerate great-circle corners that never reach the rendered path; other families keep d3's defaults), `src/utils/framePath.ts` exports `framePath(fc, project)` (the direct vertex-projection path builder for the pre-cut cylindrical layers — see the Map2D bullet), the `FIT_SPHERE` constant, and the local-area helper `localAreaScale(proj, lon, lat, d)` (px² per steradian at a point, or null off-projection / on a discontinuity). It maps (`family` × `distortion` × `azLight`) → a D3 projection; for conic / azimuthal it applies `proj.rotate([-(lambda0), -phiOrigin, rotZ]).scale(MAP_SCALE * scaleFactor).translate([VIEW_CENTER_X, VIEW_CENTER_Y])` (constants from `constants/geometry.ts`; `MAP_SCALE=100`, `VIEW_CENTER_X=400`, `VIEW_CENTER_Y=300`). Note the **negative** rotation signs. The azimuthal light-source mapping: `center` → `geoGnomonic`, `antipode` → `geoStereographic`, `infinity` → `geoOrthographic`. For the **cylindrical** family `gamma` is **ignored** (fixed at 0), and the D3 projection object is the STATIC drum frame: it carries NO rotation at all (`rotate([0, 0, 0])`) whatever the sliders do. Долгота/Параллель instead ROLL the geography INSIDE the tube — a true spherical rotation (`makeFrameRotation`) applied to the input coordinates BEFORE the projection sees them (data helpers in `utils/geoBandClip.ts`: `rotateFeatureCollection`, `rotatePolygon`, `normalizeLon`). This makes the flat map an HONEST projection: the chosen central point (λ₀, φ₀) always lands on the middle row with the LEAST distortion, and content farther away stretches toward the window edges (south pole centred ⇒ the pole is nearly true-scale while the former equator, now ±90° away, is stretched enormously) — the map never merely slides. The roll mirrors the 3D coastline matrix `projectionRotationMatrix(-lambda0, -phiOrigin, 0)` exactly (a physics test locks the agreement), so both views show the same rolled Earth. `cutFeatureCollectionToBand` also SPLITS rings at the antimeridian seam into same-hemisphere parts and nudges exact ±180° longitudes strictly inside (`LON_EDGE = 179.99999`): d3's spherical clipper degenerates on seam-touching polar geometry and inserts phantom pole-closure arcs whose fold lands as a full-width line at frame latitude ∓80° (the "inside-out map" bug). The split detects a crossing by RAW longitude difference (`|Δλ| > 180` — exact after the nudge; an unwrapping-based detection is NOT exact: for vertices nudged just inside ±180° the unwrap can collapse past the boundary and silently miss the crossing). Ring pairs where BOTH endpoints hug the rim (coastlines digitized along ±180°, e.g. the Fiji strait) splice WITHOUT interpolation — the short way round is ~0° and linear interpolation would explode to the pole. The scan starts at a vertex whose predecessor is also away from the seam, so the one unvisited wrap-around pair is usually seam-free; if it crosses anyway (rings living entirely on the seam) the tail gets its own exit and the head its own entry stub instead of being glued together. A merged chain spanning BOTH rims (odd number of crossings — Antarctica touches the seam at its start/end vertex) closes along the NEAREST BAND EDGE ±`CLIP_LAT`, where the closure coincides with the graticule rim rows instead of drawing a chord across the map. `rotatePosition` additionally restores a seam vertex's OWN side: d3's spherical rotation flips exact ±180° inputs to the opposite rim (numerical noise at the singularity), which gave Wrangel Island a phantom crossing that rendered as a thin full-width rectangle near the top of the map. The 3D tube is STATIC too (upright, identity orientation): Долгота/Параллель roll only the continents inside it, and the ray fan is a STATIC apparatus — built from the un-rotated, un-slid projection and anchored to the grid's central meridian, it never moves with the sliders. `precision(0)` is always on for the cylindrical family: the drum's graduation rows stay ruler-straight horizontal lines (no "egg"). `fitProjectionToView` overrides scale/translate to fit the 2D map to its container (the fixed `scale(100)` is only used by the 3D ray math). For the conic and azimuthal families it fits a **clipped ±85° sphere** (`FIT_SPHERE`) to the viewport, NOT a full `{type:'Sphere'}` (the pole maps to infinity for some projections, collapsing the scale). For the **cylindrical** family the 2D map follows the static-drum model. The CYLINDER IS STATIC — upright, never tilted or spun; its graduation grid (straight horizontal parallels, vertical meridians, poles at the window edges) is FIXED to it. Map2D builds exactly ONE fitted D3 projection per render and drives EVERY vector layer (graticule, coastlines, borders, Tissot circles, intersection rings) through it: for the cylindrical family `getD3Projection` bakes NO rotation into the projection whatever the sliders do, so the grid layer is automatically the static drum frame while the geography layers arrive pre-rolled. For the conic / azimuthal families that same single projection carries the rotation, so the grid follows Долгота/Параллель together with the coastlines (a regression test locks both behaviours). The GEOGRAPHY LAYER (continents, borders, Tissot circles) IS RE-PROJECTED on every slider move: Долгота/Параллель roll it via `makeFrameRotation` (`rotateFeatureCollection` / `rotatePolygon` apply the rotation to every coordinate; Map2D does this before drawing), so the continents genuinely bend around the drum — geographic meridians/parallels curve when the pole is centred, while the drum's own ruler rows under them stay straight. The VERTICAL COORDINATE STAYS PERIODIC in the drum frame: frame latitude is FOLDED into the band ±`CLIP_LAT` with period 2·`CLIP_LAT` (symmetric modulo — the edges stay on their own sides), so content past a drum rim belongs to the opposite one (scrolling past a rim would wrap to the opposite side). Geography data is PRE-ROTATED into the drum frame and THEN pre-cut at ±`CLIP_LAT` (`geoBandClip.cutFeatureCollectionToBand`, applied in Map2D after the rotation) so no ring ever crosses the wrap seam; the cut preserves interior rings (holes) — a hole is cut independently and kept whenever it survives, so lakes (e.g. the Caspian) never silently turn into solid land. Both layers share one analytic band fit (scale from the ±`CLIP_LAT` band rectangle — constant window size for every slider state; the drum never zooms and never slides), and each layer is clipped by `clipExtent` to the fixed viewport frame set AFTER the final translate (d3 clipExtent works in screen pixels but must be applied last — setting it before a later translate desynchronises it). Map2D draws exactly ONE copy of every layer through a single fitted projection — the space above and below the finite band stays empty background (the old three-stacked-copies "endless tape" read as a rendering bug and was removed) — and every layer (graticule, land, borders, Tissot circles) is rendered as ONE merged `<path>`: d3 turns the whole collection into a single `d` string, so the DOM stays tiny even for the 50m datasets. The raw height law needs no clamp: the periodic fold above maps EVERY latitude into ±`CLIP_LAT`, which is also what keeps Mercator finite (the folded argument never reaches the pole, where y → ∞). The `variant` field selects the named projection. For the **cylindrical** family the diameter (`scaleFactor`) is the cylinder radius R·`scaleFactor`; the cylinder meets the globe at the contact parallels ±arccos(`scaleFactor`). Latitudes beyond ±`CLIP_LAT` (from the cylinder axis, in the local frame) are clamped so the tube is **finite**. `gamma` (stored in **degrees** in the store) is editable only for the **azimuthal** family (the in-plane rotation of the map around the touch point); for cylindrical and conic it is fixed at 0.
- 2D `src/components/Map2D.tsx`: responsive SVG (measures its container via `ResizeObserver`) whose projection is fitted with `fitProjectionToView`; graticule built by `makeGraticule` (ALWAYS shown — there is deliberately no grid toggle; for the cylindrical family its extent is pinned to ±`CLIP_LAT`, because d3's pole-to-pole default outline folds under the periodic fold law to a phantom inner rectangle at frame ∓80° whose bottom side Antarctica paints over and whose top side the +85° land pokes past — the aligned outline puts the border exactly on the map window where the geography layers are band-cut; other families keep d3's defaults, where the outline traces the natural sphere / fan boundary), coastlines from `land50GeoJson` (≥50m detail), optional country-border layer from `countriesGeoJson`, and optional Tissot indicatrices via `d3Geo.geoCircle().radius(5)` on a 30° grid. For the cylindrical family the geography layers (land, borders, Tissot circles) are pre-rotated into the drum frame with `makeFrameRotation` + `geoBandClip.rotateFeatureCollection` / `rotatePolygon` and then band-cut, so they genuinely bend around the static drum — and they are rendered via `framePath(fc, project)` (`utils/framePath.ts`): every vertex is projected directly through a clip-free clone of the fitted projection (built only for the cylindrical family — other families never use it) and joined with straight chords, BYPASSING d3's spherical stream entirely (the pre-cut geometry needs no spherical clipping, and feeding seam-adjacent polar caps through it produced phantom pole-closure artifacts). Other families render these layers through the regular d3 path generator. The hover cursor position is un-rolled back to geographic lon/lat through the rotation's `.invert()` before it lands in the shared store. The globe always fills the viewport (with a small uniform margin) for every `scaleFactor`, fitted to the container preserving the projection's own aspect ratio (`object-fit: contain`). The cylinder diameter (cylindrical) is therefore NOT visible as a 2D size change — it shows through the map's aspect and through the 3D / Tissot intersection rings and the `Искажение площади` number. The map's top-right toolbar is a main horizontal row — **Детализация карты**, **Границы стран**, **Линии пересечения и линия разреза** and the rightmost **Точные параметры проекции** — with a vertical column hanging UNDER that last button and holding the two demo toggles: **Луч проекции по курсору** on top and **Индикатрисы Тиссо** below it (layout user decision 2026-08). The graticule is drawn on the 2D map unconditionally — the 3D globe never draws one (its globe surface shows only coastlines). When detail is off, `Map2D` draws the lightweight 110m `geoJsonData` land with 110m borders (`countries110GeoJson`) instead of the 50m datasets. The map's **bottom-right corner** shows a small glass label `Искажение площади: NN%` — the area-weighted area distortion, computed by `computeAreaDistortion` (in `projectionMapper.ts`): it samples local area-scale factors on a fine lon/lat grid and reports the mean relative area excess (equal-area projections → ~0%). The 100% reference is the area scale **at the standard parallel (where true scale = 1)**. The map's **bottom-left corner** carries a neon link to the Stepik course «Геопространственный анализ данных на Python» (https://stepik.org/a/258792).
- 3D scene `src/components/GlobeScene.tsx` composes the thin components (all flat under `components/`, no `Scene3D/` subfolder): `Globe.tsx` (transparent dark sphere with neon-blue **3D-line** coastlines — no graticule: the globe never draws one; NOT the `CanvasTexture`/orthographic variant from the old spec; the coastline GEOGRAPHY LAYER rolls with Долгота/Параллель via the rigid roll matrix passed down from `GlobeScene` (computed there ONCE as `projectionRotationMatrix(-lambda0, -phiOrigin, 0)` and shared with the hover marker) while the shell stays fixed), plus an OPAQUE continent fill (`LAND_FILL`, near-black; user decision 2026-08) triangulated by `src/utils/globeLandGeometry.ts` — rings are split at the ±180° seam (raw |Δλ| > 180 detection, both-rim pairs spliced without interpolation, tail glued into the head chain so closures run along the seam meridian — mirrors `geoBandClip`; NOTHING band-clipped so polar caps survive), each polygon is triangulated with three's own `ShapeUtils.triangulateShape` (holes preserved — the Caspian stays ocean; holes attach by bbox containment like `geoBandClip`), and the whole layer rides the SAME roll matrix as the coastlines. The triangulation runs ONCE per dataset (`triangulateLand`) and only the vertex roll re-runs per slider tick (`landPositions`). The fill rides at the SAME inflated radius as the coastline lines (a radial gap would open a dark slit along every shore at grazing camera angles) and yields depth order via `polygonOffset`, so the outlines never z-fight with the patch they trace), `AuxSurface.tsx` (fully transparent neon-orange **wireframe** of the developable surface — its own meridians + parallels; cylinder for cylindrical, cone for conic, plane for azimuthal), `IntersectionDisks.tsx` (hollow **white** rings marking the **actual** intersection of the aux surface with the globe — 0, 1 or 2 circles; the component renders nothing when the surface does not touch the globe), `LightSource.tsx` (yellow lamp at the azimuthal light position or at the conic cone apex), `Rays.tsx` (the single projection visualization — rays from the light through the globe points onto the surface), plus `CutLine.tsx` (the white surface seam/cut line) and `TouchPointPin.tsx` (the yellow azimuthal touch-point pin — a NON-interactive visual marker: the touch point is moved from the control-panel presets or by clicking the 2D map; the pin sits exactly ON the touch point, so a click handler there could only ever «move» it to where it already stands). The white apparatus lines render ONLY while the **Линии пересечения и линия разреза** toggle (`showIntersection`) is on (default off: no lines in either view until enabled); the SAME flag drives the white intersection-ring layers on the 2D map. The seam/cut LINE is **3D-only** since 2026-08 (user decision): on the flat cylindrical/conic map it used to be drawn through the middle of the window at λ₀, but the real wrap seam of the unrolled map sits at the window edges ±180°, so a centre line claimed a cut that is not there — `computeCutLineLonLat` and the map's cut-line layer were removed; do not reintroduce them. `GlobeScene` computes the developable-surface geometry once (`computeAuxSurfaceParams`, memoized on the projection params) and passes the resulting `surface` object down so all consumers share one computation and can never drift apart. The azimuthal aux-plane wireframe rotates its grid points directly by the tangent-basis quaternion so its orientation is always correct. `GlobeScene` adds `OrbitControls` (from `@react-three/drei`, `makeDefault`, pan disabled) so the user can rotate/zoom the camera; a ref to the controls instance is kept so the `_sceneResetToken` bump from `resetParams` can call `.reset()` and restore the initial camera pose. The 2D map (`Map2D.tsx`) and the 3D globe share a **hover linkage**: hovering either view reads the (lon, lat) under the cursor into the store's `hoverLonLat` and BOTH views draw the matching yellow dot (the marker is symmetric — a hover picked on the globe is mirrored on the map and vice-versa); ALL hover feedback (mirrored dots + ray) renders only while the **Луч проекции по курсору** toggle (`showHoverRay`) is on — with it off, hovering gives no feedback in either view AND neither view even tracks the hover: both `handlePointerMove` (map) and the globe's move handler return before writing `hoverLonLat`, so the shared store stays still while the cursor roams; a toggle-off mid-hover leaves a stale value that nothing renders, and the next enabling shows it until the cursor moves again — product decision 2026-08, the BRD was aligned to this behaviour); sliding the cursor off the map's globe (into the letter-boxed margin or the hidden hemisphere) or off the 3D globe CLEARS the shared hover instead of leaving a stale marker at the last position — but each view may only clear a hover ITSELF set: leaving the map never wipes a hover that came from the globe, and leaving the globe never wipes a hover that came from the map; the 3D marker is placed through the SAME coastline roll matrix, so it rides the visibly rotated continents instead of the un-rotated geographic position. Hovering the **2D map** (with `showHoverRay` on) additionally draws the cursor projection ray via `projectToAuxWorld` — the RAY is map-sourced only; hovering the 3D globe draws the mirrored dot but never the ray.
- `src/utils/auxSurfaceGeometry.ts` is the **single source of truth** for all 3D geometry: `computeAuxSurfaceParams`, `computeAuxGraticule`, `computeAuxSphereIntersections` (the real aux-surface↔globe intersection circles, in 3D world coords) and `computeAuxSphereIntersectionsLonLat` (the same circles projected back to lon/lat for the 2D map's `showIntersection` layer), `auxPointToWorld` (the single world-transform for the aux surface, shared by `AuxSurface` and the rays so they can never drift), `computeCentralMeridianRays` (the central-meridian ray fan) and `projectToAuxWorld` (the per-point ray used by the hover demo; for the cylindrical family the hovered point is FIRST rolled into the drum frame via `makeFrameRotation`, so the landing follows the rotated continent exactly like the flat map draws it), `computeTangentBasis`, `lonLatToVec3` (`RADIUS = 10`) and its inverse `vec3ToLonLat` (used by `GlobeScene` to read the cursor's lon/lat off the 3D globe for the hover linkage). Surface, ring, and rays derive from the same math so they can never drift apart. (Replaces the old `rayGeometry.ts`.) It also exposes the cut-line math `computeCutLine` (the 3D `CutLine` seam line; 3D-only — its former lon/lat map wrapper was removed with the 2D cut-line layer), the vector helpers `vec3Normalize`, and `intersectionRingToWorld(surface, ring)` — the single raw-ring→world transform (the azimuthal ring is already world-space and must NOT be transformed again) shared by the 3D `IntersectionDisks` and the 2D lon/lat wrapper so both views cannot drift. `computeCone(phi1, phi2, radius, scaleFactor)` supports both **tangent** (φ1 = φ2) and **secant** (φ1 ≠ φ2, same hemisphere) cones; the cone sits in the **signed** hemisphere of `phiOrigin` (so a southern `phiOrigin` yields a south-pointing cone) while the parallel *magnitude* uses the equatorial `30°` fallback on `|phiOrigin|`. Every cone construction site — the 2D D3 parallels (`getD3Projection`), this cone, its intersection rings and every ray builder — takes the EFFECTIVE parallel pair from `conicStdParallels(phiOrigin, stdParallel2)` (`constants/geometry.ts`: signed fallback φ₁ + φ₂ re-signed into φ₁'s hemisphere), so both views always agree on where the cone touches the Earth even when |φ₀| < 10° with a secant active. `gamma` (stored in **degrees** in the store, editable only for azimuthal) is converted to radians inside this module and inside `AuxSurface.tsx` (Three.js rotations are radians), so the rays and the wireframe stay aligned. `computeAuxSurfaceParams` honours the azimuthal `azLight` modes (`center` → rays from the globe centre (gnomonic), `antipode` → rays from the antipode (stereographic), `infinity` → parallel orthographic beams arriving along the **radial** normal). The aux-surface API is **params-object based**: `computeAuxSurfaceParams(params, radius?)`, `computeAuxSphereIntersections(params, radius?)`, `computeAuxSphereIntersectionsLonLat(params)` and `computeCutLineLonLat(params)` each take the full projection descriptor as a single `ProjectionParams` object (the old ten-argument positional lists are gone), and `coneApexWorld(surface)` reads the tilt γ from the surface itself so the apex can never drift out of the rendered cone. The cylinder always passes through the globe centre and touches it (secant, radius `scaleFactor`·R). Its axis is POLAR and STATIC (upright, identity orientation — it never tilts with φ₀; the geography rolls inside it), matching the flat map's static drum: the cylinder's surface object carries NO orientation/offset fields at all — its local frame IS the world frame (`auxPointToWorld` returns the point unchanged), and the dead parallel-light branches for the cylindrical family were removed (its light is always the globe centre). `clampLocalToSurface(surface, p)` then clamps every ray endpoint to the rendered surface's finite extent so a ray can never fly into empty space (exposed via `computeConicRayEnd(..., clamp=true)` for tests). `AuxSurface.tsx` calls `computeAuxSurfaceParams` with the same full param set so the wireframe and the rays share identical sizing, and `Rays.tsx` draws the hover ray as a polyline `start→globe→end` so the yellow globe marker lies exactly on the beam.
- The rays (`Rays.tsx`) are the **single** projection visualization in the 3D scene: a DASHED yellow fan from the light source (globe centre for cylindrical, cone apex for conic, azimuthal light position for azimuthal) through the globe points onto the aux surface, plus the dashed cursor hover ray (slightly larger dashes to match its heavier stroke; user decision 2026-08 — solid beams read as too heavy over the wireframe). The decorative "visualization methods" (normals, particles, magnetic, peel, wave, laser, construction, shadow) were removed in the simplification refactor. `CutLine.tsx` draws the developable-surface cut/peel line; `TouchPointPin.tsx` marks the azimuthal touch point. The rays are always shown (no toggle).
- `src/utils/tissot.ts` builds the Tissot indicatrices for the 2D `Map2D` overlay: `computeTissotCircles(density)` returns an array of 5°-radius spherical circles (`d3Geo.geoCircle().radius(5)`) on a `density`-degree lon/lat grid (default 30°), staggered by half a step on every other latitude row so the pattern is even. The step is clamped to a ≥10° floor — a 5°-radius circle on a denser grid is visually meaningless but explodes the work (step 1 → ~43k circles per slider tick), so steps 1–10 all collapse to the same cheap grid. `Map2D` passes the fixed `TISSOT_STEP` constant (= 2·`GRATICULE_STEP`, from `constants/geometry.ts`) as `density`, so the indicatrices sit on every SECOND graticule intersection — double spacing since the user decision of 2026-08 (the old every-15° packing read as a dense carpet). Used only when `showTissot` is on.
- `src/constants/designTokens.ts` exports the shared palette `NEON_BLUE` / `NEON_ORANGE` / `NEON_YELLOW` / `NEON_WHITE` / `BG`; both 2D and 3D components import it instead of hard-coding the hex values. `src/constants/geometry.ts` holds shared numeric constants (`MAP_SCALE`, `VIEW_CENTER_X/Y`, `CLIP_LAT`, `GRATICULE_STEP`, `TISSOT_STEP`, `FIT_MARGIN`, `RADIUS`, `RAY_COUNT`, aux-surface factors, `STD_PARALLEL_MIN_ABS` / `STD_PARALLEL_FALLBACK`) plus the standard-parallel helpers (`standardParallelDeg` / `signedStandardParallelDeg` / `conicStdParallels`) — single source so magic numbers never drift between the 2D map and the 3D scene.
- `src/store/selectors.ts` exposes `useProjectionParams()` (a memoized `ProjectionParams` slice) so consumers read the projection state as one object instead of subscribing to every field. `GlobeScene` and `Map2D` use it.
- `src/components/ui/` holds shared styling extracted from `ControlPanel.tsx`: `icons.tsx` (all SVG icons), `styles.ts`, `labels.ts`, and the reusable controls `ParamSlider.tsx` (labelled range slider with value readout + disabled/locked state) and `PresetChips.tsx` (a row of active/inactive preset buttons). ## Store shape (verified in code)
ProjectionParams (the param slice of the store, type `ProjectionParams`):
```ts
variant: ProjectionVariant;  // named projection variant — determines family/distortion/azLight
family: 'cylindrical' | 'conic' | 'azimuthalPerspective';
distortion: 'conformal' | 'equalArea' | 'equidistant';
lambda0: number;       // -180...180  central meridian
phiOrigin: number;     // -90...90    central latitude
scaleFactor: number;   // 0.9...1.1 (conic/azimuthal); 0.5...1.0 cylindrical (1.0 = cylinder diameter = Earth's, 0.5 = half)
gamma: number;         // -180...180  tilt / in-plane rotation; editable only for azimuthal
stdParallel2: number | null;          // φ2; null = tangent surface (single standard parallel); always carries the cone hemisphere's sign (φ₀ < 0 ⇒ φ₂ < 0)
azLight: 'center' | 'antipode' | 'infinity';   // azimuthal light-source mode
```
Non-param state (also on the store):
```ts
showTissot: boolean;
showBorders: boolean;                 // 2D country-border layer toggle (default false)
showIntersection: boolean;            // white apparatus lines (aux-surface∩globe rings + seam/cut line) in BOTH the 2D map and the 3D scene (default false)
geoJsonData: FeatureCollection | null;      // land-110m, source for the 3D globe
land50GeoJson: FeatureCollection | null;    // land-50m, 2D base map
countriesGeoJson: FeatureCollection | null; // countries-50m, 2D border layer (detailed mode)
countries110GeoJson: FeatureCollection | null; // countries-110m, 2D border layer (lightweight mode)
detailedMap: boolean;                       // 2D map detail toggle (default false → lightweight 110m land + 110m borders; true → 50m land + 50m borders)
geoLoading: boolean;                        // true while loadGeoData fetches the bundled geodata
geoDataError: string | null;                // friendly Russian message set when BOTH the 110m and 50m land fetches fail (null otherwise); Map2D shows it in the empty-map overlay so the user knows to reload
hoverLonLat: [number, number] | null;  // hovered (lon, lat), shared so the other view mirrors the highlight
hoverSource: 'globe' | 'map' | null;   // which view set hoverLonLat (ray drawn only for 'map')
_sceneResetToken: number;              // monotonic counter bumped by resetParams — GlobeScene snaps the 3D camera back to its initial pose on change
showHoverRay: boolean;                 // cursor projection ray in the 3D scene, shown only while the 2D map is hovered (default false)
```
Map data is bundled locally (no runtime/external API, per spec): `public/world-110m.topojson` (Natural Earth 1:110m land, used by the 3D globe), plus `public/land-50m.json` and `public/countries-50m.json` (1:50m, used by the 2D `Map2D`). All three files are **TopoJSON** (`{type:'Topology'}` with `objects.land` / `objects.countries`); despite the `.json` extension they are parsed via `topojson-client`'s `feature()`, not fetched as GeoJSON. `loadGeoData` fetches all three in parallel and stores them separately; a failed fetch for one file does not abort the others. A monotonic `_geoToken` discards stale results if a newer fetch starts before an older one resolves (so a fast remount can't overwrite fresh data with stale data); a call that starts while ANOTHER is still in flight returns immediately (React StrictMode double-mounts must not duplicate the four network requests) — a finished load always clears the flag, so a later retry still works. If BOTH the 110m and 50m land fetches fail the 2D map has nothing to render and `geoDataError` is set to a friendly Russian message («Не удалось загрузить карту. Проверьте подключение к интернету и перезагрузите страницу.»); `Map2D` shows it in its empty-map overlay (no retry button — the user reloads the page). A partial failure (any single file) stays silent because the surviving layers still produce a usable map. As of the 110m-borders change it also loads `public/countries-110m.json` (Natural Earth 1:110m Admin 0) into `countries110GeoJson`. The lightweight 2D map now draws 110m borders (`countries110GeoJson`), while the detailed map keeps 50m borders (`countriesGeoJson`); the **Границы стран** button is always visible and toggles a real border layer in both lightweight and detailed modes. `isEllipsoid` was removed — the model is **spherical** (D3 projections are spherical too; true ellipsoidal support is out of scope).

## Hard rules / conventions (from spec, enforced in code)
- Strict TypeScript: no `any` in component props; type the TopoJSON `FeatureCollection`.
- Wrap D3 projection / `pathGenerator` / ray math in `useMemo` — real-time perf requirement, never recompute per frame.
- All controls are always visible — when a parameter is locked by the selected projection variant it shows as **disabled** (not hidden), with `🔒` prefix and the locked value. The visual/physical params each have a dedicated control, labeled with the **physical terms** of the projection; controls are **context-dependent** (some shown only for certain variants, e.g. parallel 2 for secant cones, touch-point presets for azimuthal). The central-latitude slider is ONE control present for every family, labeled by the family's physical meaning: «Центральная параллель (φ₀)» (cylindrical) / «Широта точки (φ₀)» (azimuthal) / «Параллель 1 (φ₁)» (conic — there it genuinely IS the first standard parallel). The cone hemisphere has NO switch — it always follows φ₀'s sign, and `setParam` keeps an active secant φ₂ inside that hemisphere (a mixed-sign pair like [−40°, +60°] is an impossible cone). The **Тип искажения** (`distortion`) is set implicitly via the variant dropdown. The **ℹ️ Точные параметры** button lives in the 2D map's top-right toolbar (same plain-icon style as the other map buttons) and opens a read-only Geodetic Summary **modal** listing λ₀, φ₀ (labelled «Точка касания» for azimuthal), φ₁/φ₂ (conic only), the drum contact parallels ±arccos(scaleFactor) (cylindrical only), scale, γ (azimuthal), and the computed projection class. The slim top `ProjectionHeader` (the first of the left column's three parts) is a single neon strip split by a vertical line: the wide left zone is the projection dropdown (all 7 projections grouped by the three families), the narrow right zone resets the parameters.
- Earth model is spherical; do not add ellipsoid math.
- Per spec §9.3, WebGL/`<Canvas>` and SVG `d` attributes are intentionally **not** unit-tested. Existing unit tests cover the store, `projectionMapper`, `auxSurfaceGeometry`, `ControlPanel`, `ProjectionHeader`, `Map2D`, `ErrorBoundary`, and `App`.
