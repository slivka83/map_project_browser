# AGENTS.md

## Project status
Working MVP of «Carto-Space» — an interactive cartographic-projection simulator (educational tool showing the 3D Earth ↔ 2D map relationship). Client-side SPA only: **no backend, no external APIs**; all projection math runs in-browser. Product/legacy specs live in `docs/BRD.md` (business, Russian) — they may be out of date; **this `AGENTS.md` is the authoritative implementation reference.** The app UI language must be Russian.

## Commands
Run **directly from the project directory** `/mnt/d/_projects/pet_project/map_project_browser`:
- `npm run dev` — Vite dev server
- `npm run build` — `tsc -b && vite build` (typecheck + production build)
- `npm run lint` — ESLint
- `npm run test` — Vitest (`vitest run`); `npm run test:watch` for watch mode
- `npm run preview` — preview the built app

Typecheck is part of `build` (`tsc -b`); there is no separate `typecheck` script. `lint` runs before `build` in CI, so lint errors fail the build there.

## Dev workspace / DrvFS workaround (CRITICAL)
`/mnt/d` is a Windows-mounted drive (9P/DrvFS). `npm install` fails there with `ENOTDIR` on `mkdir node_modules`, and a corrupted `node_modules` dentry cannot be removed from inside the container. We keep a real `node_modules` on the **native Linux filesystem** and symlink it into the project:
- Native home for deps lives on the **persistent** WSL filesystem (NOT `/tmp`, which is wiped on every reboot): `~/mbp-deps/node_modules`, created via `npm ci` inside `~/mbp-deps` (that dir also holds `package.json` + `package-lock.json`). Use the WSL home of whichever user runs the build — typically `/home/<user>/mbp-deps`.
- In the project dir, `node_modules` is a symlink → `~/mbp-deps/node_modules` (the symlink itself lives on the Windows disk under `/mnt/d`, so it survives reboots too). `eslint.config.js` is a real native copy (or symlink). No other source/config symlinks are needed.
- `vite.config.ts` sets `server.watch.usePolling` because DrvFS emits no `inotify` events, so Vite's watcher otherwise never sees edits under `/mnt/d` (HMR won't fire). No `preserveSymlinks` is needed — sources are local.

Because the native deps and the project symlink are both persistent, **no setup is needed after a reboot** — just `npm run dev` from WSL. The one-time setup (run once from WSL): `H=~/mbp-deps; mkdir -p "$H" && cp package.json package-lock.json "$H"/ && cd "$H" && npm ci`, then `ln -sfn "$H/node_modules" /mnt/d/_projects/pet_project/map_project_browser/node_modules`. Only re-run this if the symlink/target is ever deleted. **Do NOT run `npm install`/`npm ci` inside `/mnt/d`.**

## Architecture (how it is wired)
- Three projection families: `cylindrical`, `conic`, `azimuthal`. All three have developable aux surfaces (cylinder/cone/plane) shown in 3D.
- Single Zustand store `src/store/useAppStore.ts` is the **only** source of truth; UI / 2D / 3D components only read from it or call its actions (`setParam`, `setVariant`, `setShowTissot`, `setFamily`, `resetParams`, `applyPreset`, `loadGeoData`). `setFamily(family)` switches the family **and resets to the family-default variant** (cylindrical → `mercator`, conic → `lambertConformal`, azimuthal → `gnomonic`), which in turn sets the appropriate `distortion`, `azLight`, and locked param values. `setVariant(variant)` switches the named projection variant within the current family, setting `family`, `distortion`, `azLight`, and default params accordingly. `resetParams()` resets all params to the current family/variant defaults.
- `src/utils/projectionMapper.ts` exports `getD3Projection(state)`, `computeAreaDistortion(params)`, `fitProjectionToView(proj, w, h, margin)`, `isPointerOverGlobe(path, x, y)`, and `FIT_SPHERE` constant. It maps (variant × `family` × `distortion`) → a D3 projection, then applies `proj.rotate([-(lambda0), -phiOrigin, rotZ]).scale(MAP_SCALE * scaleFactor).translate([VIEW_CENTER_X + falseEasting, VIEW_CENTER_Y + falseNorthing])` (constants from `constants/geometry.ts`; `MAP_SCALE=100`, `VIEW_CENTER_X=400`, `VIEW_CENTER_Y=300`). Note the **negative** rotation signs. The `variant` field selects the named projection: `miller` uses the Miller cylindrical formula, others use the distortion-selected law. `makeMillerProjection(scaleFactor)` implements the Miller formula: x ∝ cos φ_s, y = (5/4)·cos φ_s·ln[tan(π/4 + 2φ/5)]. Tilting a cylinder is geometrically equivalent to tilting the GLOBE relative to the (fixed, straight) cylinder — i.e. it shifts the cylinder's central latitude — so for the **cylindrical** family `gamma` is folded into `phiOrigin` (`rotate([-(lambda0), -(phiOrigin + gamma), 0])`), NOT as the third roll component (which would skew the map into an "egg"). The 2D map is the projection onto the surface: its **FRAME stays a straight rectangle** (straight surface parallels, guaranteed by `precision(0)`) while its **CONTENT (coastlines, globe graticule) shifts and skews as the cylinder tilts** — exactly what the 3D tube shows (tilting it re-lands the globe on the tube). The `projFlat` used to place the rays likewise folds gamma into phiOrigin (cylindrical) so the rays and the map always agree; `lambda0` sets the central meridian. Conic / azimuthal keep the true `gamma` roll (their orientation genuinely changes in space), so `rotZ = -gamma` there. For the **cylindrical** family the diameter (`scaleFactor`) is the cylinder radius R·`scaleFactor`; the cylinder meets the globe at the contact parallels ±arccos(`scaleFactor`), which are the (true-scale) standard parallels of the developed surface. `makeCylindricalProjection(distortion, scaleFactor)` keeps the chosen property by its height law with the standard parallel at the contact ±φ_s: conformal → secant-Mercator law (x ∝ cos φ_s, y ∝ cos φ_s·ln tan), equal-area → y ∝ sin φ / cos φ_s, equidistant → y ∝ φ (all narrow as the diameter shrinks since x ∝ cos φ_s = scaleFactor). Latitudes beyond ±`CLIP_LAT` (from the cylinder axis, in the local frame) are clamped inside each height law so the tube is **finite** — no Mercator pole infinity, exactly like the 3D tube. The cylindrical projection is built with `precision(0)` (adaptive resampling OFF): with resampling on, d3 treats the `rotate`-wrapped projection as oblique and approximates each segment with great-circle arcs, which bends the straight top/bottom parallels into an arc so the whole map looks like an **"egg"**; with it off every parallel stays a straight horizontal line (a proper rectangular band), and the graticule / coastline vertices keep it smooth. Tilting the cylinder (`gamma`) carries the low-distortion band to the new cylinder equator in the 3D scene (Antarctica on it keeps the least scale error) and `computeAreaDistortion` references ±φ_s so the reported distortion still drops as the diameter shrinks. The unrolled map's **aspect genuinely changes** with the diameter (a smaller cylinder → a narrower / taller map) — the real geometric effect, which `fitProjectionToView` preserves by fitting the globe to the viewport (`object-fit: contain`), so the diameter shows through the projection's aspect rather than its size. The azimuthal family's projection is selected by `azLight` (the interactive light source): `center` → `geoGnomonic`, `antipode` → `geoStereographic`, `infinity` → `geoOrthographic`, `math` → the `distortion`-selected analytic projection (equal-area / equidistant; conformal azimuthal is itself stereographic). Conic projections use `parallels([phi1, phi2])` where `phi1 = signedStandardParallelDeg(phiOrigin)` keeps `phiOrigin`'s *sign* (so a southern `phiOrigin` yields a southern standard parallel matching the 3D aux cone; falls back to `±30°` when `|phiOrigin| < 10`), and `phi2 = stdParallel2` when set (secant cone) or `phi1` (tangent). The 3D cone geometry derives the parallel *magnitude* via the shared `standardParallelDeg` helper and the hemisphere from the sign of `phiOrigin`, so the 2D map and the 3D aux surface always agree on where the cone touches the globe. `fitProjectionToView` overrides scale/translate to fit the 2D map to its container (the fixed `scale(100)` is only used by the 3D ray math). It fits a **clipped ±85° sphere** (`FIT_SPHERE`) to the viewport, NOT a full `{type:'Sphere'}`: for `geoConicConformal` the pole maps to infinity, so a full-Sphere `fitExtent` collapses the scale to near-zero (the globe renders as an empty half-disk). The clip keeps the fitted scale finite. Because the map is always fitted to fill the viewport (`object-fit: contain`), the cylinder diameter is NOT visible as a size change — the map occupies the full area for every `scaleFactor`; the diameter shows through the projection's aspect (equal-area / equidistant narrow as the cylinder shrinks) and through the 3D / Tissot intersection rings and the `Искажение площади` number. Conformal (secant Mercator) DOES change with `scaleFactor` (its standard parallel is the contact ±arccos(`scaleFactor`)), so its 2D map and the `Искажение площади` number both move with the diameter, exactly like the rings / Tissot. For conic/azimuthal `scaleFactor` is a plain zoom, but the fitted map still always fills the viewport. (For `azLight='infinity'` the 2D map becomes an orthographic hemisphere view, by design.)
- 2D `src/components/Map2D.tsx`: responsive SVG (measures its container via `ResizeObserver`) whose projection is fitted with `fitProjectionToView`; graticule, coastlines from `land50GeoJson` (≥50m detail), optional country-border layer from `countriesGeoJson`, and optional Tissot indicatrices via `d3Geo.geoCircle().radius(5)` on a 30° grid. The globe always fills the viewport (with a small uniform margin) for every `scaleFactor`, fitted to the container preserving the projection's own aspect ratio (`object-fit: contain`). The cylinder diameter (cylindrical) is therefore NOT visible as a 2D size change — it shows through the map's aspect (equal-area / equidistant narrow as the cylinder shrinks) and through the 3D / Tissot intersection rings and the `Искажение площади` number. Conformal (secant Mercator) also moves with `scaleFactor` (its standard parallel is the contact), so its 2D map and the number both shift with the diameter. (For `azLight='infinity'` the 2D map becomes an orthographic hemisphere view, by design.) The **Индикатрисы Тиссо**, **Детализация карты** and **Границы стран** buttons are always visible together as a single horizontal row in the map's top-right corner. When detail is off, `Map2D` draws the lightweight 110m `geoJsonData` land with 110m borders (`countries110GeoJson`) instead of the 50m datasets. The map's **bottom-right corner** shows a small glass label `Искажение площади: NN%` — the area-weighted area distortion of the current projection settings, computed by `computeAreaDistortion` (in `projectionMapper.ts`): it samples local area-scale factors on a fine lon/lat grid and reports the mean relative area excess (equal-area projections → ~0%). The 100% reference is the area scale **at the standard parallel (where true scale = 1)**. For the cylindrical family the standard parallels are the surface–globe intersections at ±arccos(`scaleFactor`) (a tangent cylinder is the single-intersection limit at `scaleFactor` = 1), so an immersed (secant) cylinder — two intersections — makes the distortion **drop** as the cylinder diameter shrinks, matching the 3D intersection rings; conic/azimuthal treat `scaleFactor` as a true zoom and reference the projection centre. Cells that straddle the antimeridian, fold onto themselves, or are stretched far past the centre scale (projection discontinuities) are skipped so they can't masquerade as distortion. The map's **bottom-left corner** carries a neon link to the Stepik course «Геопространственный анализ данных на Python» (https://stepik.org/a/258792).
- 3D scene `src/components/GlobeScene.tsx` composes five thin components (all flat under `components/`, no `Scene3D/` subfolder): `Globe.tsx` (transparent dark sphere with neon-blue **3D-line** coastlines + graticule — NOT the `CanvasTexture`/orthographic variant from spec §6), `AuxSurface.tsx` (fully transparent neon-orange **wireframe** of the developable surface — its own meridians + parallels; cylinder for cylindrical, cone for conic, plane for azimuthal; the azimuthal plane is the projection plane tangent to the globe), `IntersectionDisks.tsx` (hollow white neon rings marking the **actual** intersection of the aux surface with the globe — 0, 1 or 2 circles; a cylinder of radius R·scaleFactor yields two circles when immersed, one when tangent, none when it encloses the sphere; the component renders nothing when the surface does not touch the globe). **The intersection follows the real geometry of the (possibly tilted) surface:** rotation about the tube's own vertical axis does not move the contact circles, but the **tilt (gamma) DOES move them** (a tilted cylinder's axis leaves the poles, so the contact circles travel), and shrinking the **diameter** also moves them (smaller immersed cylinder → circles converge toward the equator). Every ring is pushed through `auxPointToWorld` — the exact transform the aux-surface wireframe uses — so it always sits on the true intersection of the tilted surface with the globe. **For conic / azimuthal the 2D `Map2D` white intersection lines show the SAME tilted contact circle as the 3D ring** (via `computeAuxSphereIntersectionsLonLat`, which runs every ring point through `auxPointToWorld`). For the **cylindrical** family the map is the unrolled tube and does not know the tube's tilt, so its white intersection lines are drawn with `gamma = 0` — the un-tilted cylinder meets the globe at the two contact parallels ±φ_s — while the 3D ring separately follows the tilted tube. The 2D canvas itself stays a plain rectangle, its FRAME invariant; for the cylindrical family the whole CONTENT (coastlines, graticule, intersection lines) is invariant under the tilt because the rays are bound to the tube and rotate with it — the map is the tube's own-frame development. `LightSource.tsx` (the projection's **light source** — a point lamp at the globe centre/antipode for azimuthal, and the conic apex marker; nothing is drawn for the cylindrical family since the globe is simply unrolled onto the cylinder), and `Rays.tsx` (yellow light-beam fan showing the projection: each ray runs from the light source, through the point on the globe at the central meridian, to the point where that globe point lands on the **auxiliary surface** — the unrolled surface IS the 2D map). The fan is **analytic** (computed by `computeCentralMeridianRays` in `auxSurfaceGeometry.ts`): the source is the globe centre for cylindrical / azimuthal-`center` / conic-apex, the antipode for azimuthal-`antipode`, and a parallel beam along the radial normal for azimuthal-`infinity`; every ray endpoint is placed with `auxPointToWorld` so it coincides exactly with `AuxSurface`'s wireframe, and small neon markers sit at the globe point and at the surface landing. For the **cylindrical** family the whole ray is a **rigid two-segment beam attached to the tube**: the light source is the cylinder axis (local origin), the globe marker rides on the cylinder's front generator at the **true globe latitude** (local `[R·cos lat, R·sin lat, 0]`), and the landing uses the projection's own y — so start→globe→landing is genuinely bent (the marker sits on the globe sphere and "travels" along it as the tube tilts), yet the ENTIRE ray turns rigidly WITH the cylinder under any tilt (`gamma`) because all three points live in the cylinder's local frame and share `auxPointToWorld`. Leaving the globe at the raw `(λ₀, lat)` world point pinned it to the stationary globe so only the endpoint moved — the "not rotating" look. All three points derive from `auxPointToWorld` so they can never desync from the wireframe. It renders with `depthTest={false}` so the in-globe portion stays visible, and as **dashed** formula vectors in `math` mode; it renders independently of whether the geo dataset has loaded. Hovering the **2D map** (with `showHoverRay` on) draws the cursor projection ray via `projectToAuxWorld` and the shared yellow highlight marker on both views — directly showing the “globe point → map point” link (the aux surface, unrolled, is the 2D map). Hovering the **3D globe** does **not** draw the ray or the marker at all (the hover highlight is driven solely by the 2D map). `GlobeScene` adds `OrbitControls` (from `@react-three/drei`, `makeDefault`, pan disabled) so the user can rotate/zoom the camera and see the aux surface's true 3D orientation — without it, a tangent plane on the visible hemisphere always appears to face the viewer. The azimuthal aux-plane wireframe rotates its grid points directly by the tangent-basis quaternion (not via the group `quaternion` prop) so its orientation is always correct. `LightSource` also renders a small `Html` label next to the marker naming the active light mode (Центр / Антипод / ∞ / Вершина конуса). The 2D map (`Map2D.tsx`) and the 3D globe share a **hover linkage**: hovering either view reads the (lon, lat) under the cursor (`proj.invert` for the SVG, `vec3ToLonLat` for the 3D pick-sphere) into the store's `hoverLonLat` and the other view draws a matching yellow marker, so a point is cross-highlighted across both projections.
- `src/utils/auxSurfaceGeometry.ts` is the **single source of truth** for all 3D geometry: `computeAuxSurfaceParams`, `computeAuxGraticule`, `computeTangencyRing`, `computeAuxSphereIntersections` (the real aux-surface↔globe intersection circles), `auxPointToWorld` (the single world-transform for the aux surface, shared by `AuxSurface` and the rays so they can never drift), `computeCentralMeridianRays` (the central-meridian ray fan) and `projectToAuxWorld` (the per-point ray used by the hover demo), `computeTangentBasis`, `lonLatToVec3` (`RADIUS = 10`). Surface, ring, and rays derive from the same math so they can never drift apart. (Replaces the old `rayGeometry.ts`.) `computeCone(phi1, phi2, radius, scaleFactor)` supports both **tangent** (φ1 = φ2) and **secant** (φ1 ≠ φ2, same hemisphere) cones; the cone sits in the **signed** hemisphere of `phiOrigin` (so a southern `phiOrigin` yields a south-pointing cone) while the parallel *magnitude* uses the equatorial `30°` fallback on `|phiOrigin|`. `gamma` (stored in **degrees** in the store) tilts the cylinder/cone/plane for oblique & transverse aspects — it is converted to radians inside this module (`gammaRad`) and inside `AuxSurface.tsx` (Three.js rotations are radians), so the rays and the wireframe stay aligned. `computeCentralMeridianRays` honours the azimuthal `azLight` modes (`center` → gnomonic, `antipode` → stereographic, `infinity` → parallel orthographic beams arriving along the **radial** normal, `math` → centre beams). `computeAuxSurfaceParams` now takes the full projection descriptor (`distortion`, `azLight`, and optional `variant` in addition to family/λ₀/φ₀/scale/φ₂/γ). The **cylinder is equatorial and always touches the globe** (axis through the poles); `phiOrigin` chooses which parallel is centred on the 2D map / the standard parallel, but the cylinder does **not** translate in 3D and the central-meridian rays are computed with the **no-shift** projection (`phiOrigin = 0`) so the ray fan is also invariant under the central-latitude slider (variant A). The cylinder's 3D **orientation** is taken from the *exact* d3 rotation matrix (`projectionRotationMatrix(lambda0, 0, gamma)`, built from d3's own `geoRotation`) — NOT a naive `Rx(gamma)` tilt — so the tilted / transverse cylinder, its wireframe and the 2D map all agree (a plain `Rx(gamma)` tilt is geometrically wrong for `gamma ≠ 0`: the rays would not land on the rendered surface). Its **height depends on the distortion + diameter** (a different `Тип искажения` yields a different-looking cylinder), measured at `phiOrigin = 0`. The **azimuthal plane disk** is sized from the actual D3 projection of the fitted ±`CLIP_LAT` band (so a Mercator/equirectangular/gnomonic map — which sends high latitudes far out — still has a surface big enough for every ray to land on), capped at `AUX_SIZE_CAP · AUX_LENGTH · radius` (`AUX_SIZE_CAP = 4`) so a gnomonic disk that runs to infinity stays finite. `clampLocalToSurface(surface, p)` then clamps every ray endpoint to the rendered surface's finite extent so a ray can never fly into empty space: cylinder → local Y within `±height/2`; **cone → radially scaled toward the apex** (so the endpoint stays *on the lateral surface* — a naive Y-clamp would flatten the cone into a cap and break the geometry); plane → radial distance within `size/2`. The clamp is applied inside **both** `computeCentralMeridianRays` and `projectToAuxWorld` (and exposed via `computeConicRayEnd(..., clamp=true)` for tests). `AuxSurface.tsx` calls `computeAuxSurfaceParams` with the same full param set so the wireframe and the rays share the identical sizing, and `Rays.tsx` draws the hover ray (like every ray in the static fan) as a polyline `start→globe→end` so the yellow globe marker lies exactly on the beam, and the "globe point → map point" link is explicit (the aux surface, unrolled, is the 2D map).
- `src/constants/designTokens.ts` exports the shared palette `NEON_BLUE` / `NEON_ORANGE` / `NEON_YELLOW` / `NEON_WHITE` / `BG`; both 2D and 3D components import it instead of hard-coding the hex values. `src/constants/geometry.ts` holds shared numeric constants (`MAP_SCALE`, `VIEW_CENTER_X/Y`, `CLIP_LAT`, `FIT_MARGIN`, `RADIUS`, `RAY_COUNT`, aux-surface factors, `STD_PARALLEL_MIN_ABS` / `STD_PARALLEL_FALLBACK`) and the deduplicated `standardParallelDeg` helper — single source so magic numbers never drift between the 2D map and the 3D scene.
- `src/store/selectors.ts` exposes `useProjectionParams()` (a memoized `ProjectionParams` slice) so consumers read the projection state as one object instead of subscribing to every field. `GlobeScene` and `Map2D` use it.
- `src/components/ui/` holds shared styling extracted from `ControlPanel`: `icons.tsx` (all SVG icons), `styles.ts` (`labelClass`, `activeTab`, `inactiveTab`, `iconBtn`, `iconBtnPlain`, `iconGlow`), and `labels.ts` (the Russian `FAMILY_*` / `DISTORTION_*` label maps, previously duplicated in `ControlPanel` and `EpsgCatalog`, and the variant option lists from `projectionVariants.ts`). Keep cross-component UI here, not in a component file, to avoid `react-refresh` export warnings.
- `src/components/ProjectionCatalog.tsx`: modal rendered via `createPortal` to `document.body` listing all projections grouped by family (cylindrical, conic, azimuthal) with text search. Selecting a row calls `setVariant(variant)` and closes.
- `src/components/GlobeScene.tsx` computes the developable-surface geometry once (`computeAuxSurfaceParams`, memoized on the projection params) and passes the resulting `surface` object down to `AuxSurface`, `IntersectionDisks` and `LightSource`, so all three share one computation and can never drift apart. For pseudocylindrical and mathematical families the surface is `null` — those components are not rendered.
- `src/components/Dropdown.tsx` is a generic `Dropdown<T extends string>` (a `button` + popover, variants `button` / `inline`) — it backs the math-model selector in `ControlPanel.tsx` and the EPSG-filter selects in `EpsgCatalog.tsx`. It is unit-tested (`Dropdown.test.tsx`).

Mirror of `EpsgCatalog`'s modal styling.

## Store shape (verified in code)
```ts
variant: ProjectionVariant;  // named projection variant (e.g., 'mercator', 'gnomonic') — determines family/distortion/azLight
family: 'cylindrical' | 'conic' | 'azimuthal';
distortion: 'conformal' | 'equalArea' | 'equidistant';
lambda0: number;       // -180...180  central meridian
phiOrigin: number;     // -90...90    central latitude
scaleFactor: number;   // 0.9...1.1 (conic/azimuthal); 0.5...1.0 cylindrical (1.0 = cylinder diameter = Earth's, 0.5 = half)
falseEasting: number;  // -1000...1000
falseNorthing: number; // -1000...1000
gamma: number;         // -180...180  tilt / 3rd rotation → oblique & transverse aspects
stdParallel2: number | null;          // φ2; null = tangent surface (single standard parallel)
azLight: 'center' | 'antipode' | 'infinity' | 'math';   // azimuthal light-source mode
showTissot: boolean;
showBorders: boolean;                 // 2D country-border layer toggle (default false)
showIntersection: boolean;            // 2D white lines where the aux surface meets the globe (default false; the 3D scene always draws them)
hoverLonLat: [number, number] | null;  // hovered (lon, lat), shared so the other view mirrors the highlight (spec §2)
hoverSource: 'globe' | 'map' | null;   // which view set hoverLonLat (ray drawn only for 'map')
showHoverRay: boolean;                 // cursor projection ray in the 3D scene, shown only while the 2D map is hovered (default false)
geoJsonData: FeatureCollection | null;      // land-110m, source for the 3D globe
land50GeoJson: FeatureCollection | null;    // land-50m, 2D base map
countriesGeoJson: FeatureCollection | null; // countries-50m, 2D border layer (detailed mode)
countries110GeoJson: FeatureCollection | null; // countries-110m, 2D border layer (lightweight mode)
detailedMap: boolean;                       // 2D map detail toggle (default false → lightweight 110m land + 110m borders; true → 50m land + 50m borders)
geoLoading: boolean;                        // true while loadGeoData fetches the bundled geodata (late/duplicate fetches are ignored via a request token)
```
Map data is bundled locally (no runtime/external API, per spec): `public/world-110m.topojson` (Natural Earth 1:110m land, used by the 3D globe), plus `public/land-50m.json` and `public/countries-50m.json` (1:50m, used by the 2D `Map2D`). All three files are **TopoJSON** (`{type:'Topology'}` with `objects.land` / `objects.countries`); despite the `.json` extension they are parsed via `topojson-client`'s `feature()`, not fetched as GeoJSON. `loadGeoData` fetches all three in parallel and stores them separately; a failed fetch for one file does not abort the others. As of the 110m-borders change it also loads `public/countries-110m.json` (Natural Earth 1:110m Admin 0, redistributed via `topojson/world-atlas`) into `countries110GeoJson`. The lightweight 2D map now draws 110m borders (`countries110GeoJson`), while the detailed map keeps 50m borders (`countriesGeoJson`); the **Границы стран** button is always visible and toggles a real border layer in both lightweight and detailed modes. `isEllipsoid` was removed — the model is **spherical** (D3 projections are spherical too; true ellipsoidal support is out of scope for the MVP).

## Hard rules / conventions (from spec, enforced in code)
- Strict TypeScript: no `any` in component props; type the TopoJSON `FeatureCollection`.
- Wrap D3 projection / `pathGenerator` / ray math in `useMemo` — real-time perf requirement, never recompute per frame.
- All controls are always visible — when a parameter is locked by the selected projection variant it shows as **disabled** (not hidden), with `🔒` prefix and the locked value. The visual/physical params each have a dedicated control, labeled with the **physical terms** of the projection: cylindrical — **Диаметр цилиндра** (`scaleFactor`), **Поворот вокруг Земли** (`lambda0`), **Угол наклона цилиндра** (`gamma`); conic — **Масштаб** (`scaleFactor`), **Центральный меридиан** (`lambda0`), **Стандартная параллель 1** (`phiOrigin`), **Наклон конуса** (`gamma`), **Параллель 2** (`stdParallel2`); azimuthal — **Расстояние до плоскости** (`scaleFactor`), **Долгота точки касания** (`lambda0`), **Широта точки касания** (`phiOrigin`), **Вращение плоскости** (`gamma`), plus a read-only **Источник света** label. The **Тип искажения** (`distortion`) is set implicitly via the variant dropdown (each named variant prescribes its own distortion model, light source, and locked-parameter defaults). ## Gotchas an agent will likely miss
- **Native `<select>` popups ignore CSS `background` on most browsers (they render white).** The app uses a single custom dark dropdown `src/components/Dropdown.tsx` (a `button` + popover, variants `button` / `inline`) — it backs the math-model selector in `ControlPanel.tsx` and the EPSG-filter selects in `EpsgCatalog.tsx`. It is generic over the option value type. Do NOT replace it with a native `<select>` — keep it custom so the dark theme holds.
- `falseEasting` / `falseNorthing` exist in the store and projection math but have **no sliders in the UI** (only `lambda0`, `phiOrigin` [conic/azimuthal], `scaleFactor` are exposed). Don't assume they're wired to controls.
- The three family buttons in `ControlPanel` are a single segmented control (overlapping borders via `-ml-px`, `z-10` on the active one) — keep the segmented look when editing.
- The EPSG modal is a fixed `920px × 80vh` with `table-fixed` + `<colgroup>` so column widths never shift when filtering. Keep fixed widths when editing that table.

## CI
`.github/workflows/ci.yml` runs `npm ci` → `lint` → `build` → `test` on push/PR (GitHub-hosted Linux, no DrvFS quirks). Tests run with `npm run test` (Vitest, jsdom). `src/__tests__/docsConsistency.test.ts` is the doc↔code guard: it fails the build if AGENTS.md / `docs/BRD.md` / `docs/specification.md` drift from the real source (broken `src/...` references, missing component files, dropped store fields/exports, or wrong constants). Keep that test in sync whenever you rename a file, drop an export, or change a documented constant. In addition `src/__tests__/physics.test.ts` is the large **physics** suite that locks in the geometric invariants of the product: globe↔map projection round-trips and central-meridian x-centering for every `family`×`distortion`, the "globe point → map point" ray linkage (each ray's landing round-trips through `auxPointToWorld`; for the cylindrical family the ray is a rigid two-segment beam so its globe marker stays on the globe sphere yet travels with the tube under tilt rather than the raw `(λ₀, lat)` world point), Tissot indicatrix behaviour (equal-area ≈ constant area, conformal ≈ circular + isotropic scale, non-conformal clearly distorts), aux-surface↔globe intersection counts (cylinder r<R → 2 circles, r=R → 1 tangent, r>R → 0; azimuthal tangent cap centroid ≈ touch point; secant cone passes both standard parallels), area-distortion invariants (equal-area ≈ 0% at any diameter; conic/azimuthal invariant under `scaleFactor`), and globe-geometry sanity. When you change `auxSurfaceGeometry.ts`, `projectionMapper.ts`, or `tissot.ts`, extend these tests rather than loosening tolerances.
